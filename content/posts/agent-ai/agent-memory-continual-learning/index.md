你可能遇到过这样的场景：

> “这个项目的时间要按用户所在时区显示，我上次已经说过了。”<br>
> “抱歉，我会记住。”

这一轮改好了。过几天换一个页面，它又把服务器时间直接显示了出来。

让人疲惫的，是同一份纠正没有积累下来：每次合作，都像在重新带一个刚入职的同事。我们希望 AI 越用越顺手，至少别再踩已经指出的坑。

**要做到这一点，系统得让一次纠正留下持久变化，并证明这种变化能改善后续行为。** 保存一段记忆只是其中一步；检索、执行、验证和更新，任何一处断开，都可能让错误重演。

这也给“递归自我改进”（Recursive Self-Improvement，**RSI**）提供了一个具体入口：当 AI 能从错误中改进自己，我们能否进一步让它改进“发现错误、学习经验、验证改进”的方法？

<!--more-->

## 1 同样的错误可能有不同原因

继续用时区问题作例子。表面上都是“又忘了”，背后的故障却可能完全不同。

{{< codex-table label="重复犯错的原因与对应修复" >}}
| 故障发生在哪 | 时区示例 | 应该修什么 |
| --- | --- | --- |
| 没有保存 | 纠正只留在上一段对话里 | 把适用规则写入持久状态 |
| 没有取出 | 规则已保存，新任务没有检索到 | 改检索、触发时机与上下文组织 |
| 记错了范围 | 把“按用户时区显示”概括成“所有时间加八小时” | 保留条件、对象与例外 |
| 没有落实 | 能复述规则，写代码时仍绕过统一格式化函数 | 把经验连接到工具、流程和检查 |
| 能力不足 | 知道要处理时区，却不会处理跨日或夏令时 | 改工具、补训练或调整任务分工 |
| 规则过期 | 项目已改接口，仍照搬旧经验 | 版本管理、冲突处理与重新验证 |
{{< /codex-table >}}

这张表是排查问题的工程框架。它提醒我们：**先定位经验在哪一步失效，再决定要不要增加记忆或训练模型。**

更长的上下文可以缓解信息放不下的问题，却不会自动完成筛选与落实。2023 年的 *Lost in the Middle* 在当时测试的模型和任务上发现，关键信息所在的位置会影响表现，放在中间时尤其容易被忽略。这提供了一个至今仍值得测试的问题：系统是否真正用上了已有信息，而不能拿历史实验的退化幅度推断今天每个模型的表现。[Lost in the Middle](https://arxiv.org/abs/2307.03172v3)

## 2 记忆和学习究竟改变了什么

讨论 AI 有没有“学会”，最有用的追问是：**这次交互之后，下一次运行的什么东西变了？**

{{< codex-table label="AI适应机制与发生变化的位置" >}}
| 机制 | 变化保存在什么地方 | 时区问题中的例子 |
| --- | --- | --- |
| 当前上下文适应 | 这一轮的输入、示例与反馈 | 看完纠正，当场修好页面 |
| 外部记忆 | 文件、数据库、可检索的经验条目 | 下次找到项目的时间约定 |
| 技能与流程积累 | 可复用程序、工具封装、执行步骤 | 自动调用统一日期工具并检查边界 |
| 参数学习 | 模型权重或可训练模块 | 通过训练改善日期推理与工具使用能力 |
| 系统自我修改 | Agent 的检索、调度、验证等代码 | 发现漏检规律，修改自己的工作流程 |
{{< /codex-table >}}

这些机制可以并存。它们也不是必须逐级通关的路线：一个系统可以长期使用固定模型，依靠外部记忆和工具改善表现；另一个系统可以更新权重，却没有完善的跨会话记忆。

本文主要把 **Agent Memory** 用于讨论外部记忆。更广义的研究还包含参数记忆和隐式状态记忆，因此不能把“Memory 永远不改权重”当成整个领域的定义。2025 年底提出、2026 年修订的记忆综述，就分别从记忆的实现形式、功能以及形成和检索过程组织这个领域。[Memory in the Age of AI Agents](https://arxiv.org/abs/2512.13564v2)

### 冻结模型也可以组成会学习的系统

假设底层模型始终不变，但 Agent 保存了上次失败的原因，下一次据此选择更好的动作，而且这种改善可以跨任务复现。那么，整个系统已经发生了基于经验的适应。

Voyager 提供了一个直观例子：它在 Minecraft 中积累可执行代码形式的技能，检索和组合这些技能，利用环境反馈继续修正；底层语言模型通过黑盒调用使用，无需为此微调。这里积累下来的是 Agent 的技能库。[Voyager](https://arxiv.org/abs/2305.16291v2)

因此，判断是否学到了东西，要同时看**持久变化、行为收益和迁移范围**。只盯着模型权重，会漏掉系统层的学习；只看到多了一个文件，也无法证明行为改善。

## 3 一条记忆怎样才能改变下一次行动

聊天记录保存了“发生过什么”。要指导下一次工作，还需要把它整理成有依据、有条件的经验。

可以把有用的内容分成三类：

- **事件**：上次某个页面把 UTC 时间当成本地时间，导致日期错了一天。
- **事实与约定**：这个项目存储 UTC，展示时使用用户选定的时区。
- **操作方法**：修改日期显示前检查字段语义，使用统一格式化入口，并运行跨日用例。

同一件事可以生成三种记忆，但三者不能互相替代。事件让经验可追溯，约定告诉系统什么应当成立，操作方法决定接下来怎么做。

{{< mermaid >}}
flowchart TD
  A[任务结果与纠正] --> B[记录证据和适用范围]
  B --> C[核对旧条目并更新记忆]
  C --> D[新任务开始前检索]
  D --> E[检查当前条件并执行]
  E --> F[用任务结果验证]
  F --> G{经验仍然有效吗}
  G -->|有效| H[保留并记录验证]
  G -->|失效或冲突| B
  H --> D
{{< /mermaid >}}

*图中是一个工程闭环：写入、读取和验证需要一起设计。*

### 写下能执行的规则

“以后注意时区”很容易写，也很难验收。一条更可用的记忆，可以长成下面这样。**这是示例设计，不对应某个真实项目的测试结果。**

{{< codex-table label="一条可执行经验的记录示例" >}}
| 字段 | 内容 |
| --- | --- |
| 适用范围 | 项目 A 中代表具体时刻的字段与显示页面 |
| 已确认约定 | 接口传递带时区信息的时间；存储使用 UTC；展示按用户时区 |
| 触发条件 | 新增或修改日期显示、时间筛选与导出功能 |
| 执行动作 | 先核对接口语义，再使用项目统一日期工具；禁止手工固定加八小时 |
| 验证办法 | 检查跨日、不同用户时区；涉及夏令时地区时检查切换边界 |
| 证据与失效条件 | 关联接口说明、修复记录与测试；接口或日期工具变更后重新验证 |
{{< /codex-table >}}

还要区分“具体时刻”和“生日这类纯日期”。如果把所有日期都强行做时区转换，新的规则反而会制造新错误。**经验的适用边界，也是经验的一部分。**

### 检索只是中间一步

把过去的经验放进向量数据库，确实能帮助找到语义相近的内容。但“相近”不代表属于同一项目、同一版本，或拥有同样的适用条件。本文建议先按项目、对象、有效时间过滤，再结合语义检索；执行前核对关键证据。

在关键约束上，还可以把经验进一步落实到代码：统一工具、类型约束、校验器与回归用例。这样，即使 Agent 某次没想起那条笔记，执行路径仍有机会拦住错误。

研究中的外部记忆也早已超出“存文本、做相似度搜索”的范围：MemGPT 研究上下文内外的分层管理；A-MEM 研究记忆条目的关联与演化；Mem0 研究从对话中抽取、整合并检索重要信息。它们分别改善记忆链路的不同部分。[MemGPT](https://arxiv.org/abs/2310.08560v2)、[A-MEM](https://arxiv.org/abs/2502.12110v11)、[Mem0](https://arxiv.org/abs/2504.19413v1)

<details>
<summary>展开阅读：RAG、记忆与总结的区别</summary>

RAG 描述一种把检索结果交给生成模型使用的方式。记忆系统可以用 RAG 读取经验，但还需要回答：哪些新经历值得写入、旧结论如何修订、冲突怎么处理、什么应当失效。两者存在重叠，不能简单按“有没有向量数据库”区分。[记忆综述中的概念边界](https://arxiv.org/abs/2512.13564v2)

反复总结也可能丢掉有用细节。ACE 将上下文当作持续维护的经验手册，通过生成、反思、整理，以及结构化的增量更新来积累策略，针对的正是整体重写时细节被逐步压掉的问题。对时区示例而言，摘要若只剩“时间要统一”，就已经丢失了最关键的存储与展示区别。[ACE](https://arxiv.org/html/2510.04618v3)

一个实用做法是保留简短规则及原始证据的链接，允许删除、纠正和版本回退。历史内容中的假设应继续标为假设；外部材料中的命令也不能因为被保存，就自动获得执行权限。

## 4 反思要靠什么证明有用

“我应该更仔细”“下次会检查边界条件”，听起来像吸取了教训，却没有说明哪一步会改变。

有用的反思应把三件事接起来：**可观察的失败、可修改的原因、可以验证的新动作。** 例如，页面日期偏移来自错误解释 UTC 字符串；候选修复是统一解析入口；验证依据是跨日用例与实际渲染结果。

相关研究需要分开理解：

{{< codex-table label="三类反思与纠错机制" >}}
| 研究 | 怎样利用反馈 | 留下什么变化 |
| --- | --- | --- |
| [Self-Refine，2023](https://arxiv.org/abs/2303.17651v2) | 同一模型生成、评价并修改答案 | 改善当前任务的输出，方法本身不要求训练 |
| [Reflexion，2023](https://arxiv.org/abs/2303.11366v4) | 将任务反馈转成文字反思，保留给后续尝试 | 更新经验记忆，不更新模型权重 |
| [SCoRe，2024](https://arxiv.org/html/2409.12917v1) | 用多轮强化学习训练纠错行为 | 改变模型参数，让后续推理更会修正错误 |
{{< /codex-table >}}

这也解释了为什么不能只问“让模型反思有没有用”。同一个词，可能指多生成一轮文字，也可能指带结果反馈的试错，或者专门训练出来的纠错能力。

2023 年的 *Large Language Models Cannot Self-Correct Reasoning Yet* 研究了缺少外部反馈的内在纠错，在当时的推理实验中观察到失败，甚至性能下降。这个结论有明确的模型、任务和反馈条件，不能推成“所有模型永远无法自我纠错”。[原研究](https://deepmind.google/research/publications/48252/)

SCoRe 则表明，纠错行为可以成为训练目标：训练阶段利用正确性奖励，引导模型把错误答案改对，同时抑制把正确答案改错；测试时不要求每一轮都由外部裁判提供纠正。**训练时获得了可靠信号，与推理时只说一句“再想想”，是不同条件。**[SCoRe 方法与实验](https://arxiv.org/html/2409.12917v1)

对于工程系统，我会优先寻找可核查的反馈：测试是否通过、工具实际返回了什么、页面最终呈现如何、任务状态有没有改变。对于写作风格等难以自动判定的问题，则需要明确偏好和人工反馈；另一个模型的赞同可以作为线索，不能直接当成事实正确的证明。

## 5 持续学习还要解决旧能力退步

当经验已经能稳定积累，新的问题会出现：能不能把它变成更通用、更省成本的能力？

假如每次处理日期都要检索大量记录、经过多轮提示才能写对，那么复用工具、整理技能，以及有针对性的训练，都值得比较。但一条项目约定通常仍适合留在外部：它需要可编辑、可撤销，也可能明天就变。是否训练，应取决于错误的性质与重复出现的范围。

### 持续学习是一种长期要求

机器学习中的持续学习，关心在陆续到来的数据或任务上学习，同时保留已有知识和能力。它可以分批进行，不要求每收到一条消息就更新权重。对参数学习而言，核心困难之一是**灾难性遗忘**：新任务的训练改动了旧任务依赖的参数，让原来会做的事情退步。[持续学习综述](https://arxiv.org/html/2404.16789v3)

常见方法试图从不同位置减少干扰：

{{< codex-table label="参数持续学习的主要思路" >}}
| 思路 | 直观理解 | 需要付出的代价或保留的限制 |
| --- | --- | --- |
| 经验回放 | 学新题时，也复习有代表性的旧题 | 要管理旧数据、采样比例与额外计算 |
| 约束参数更新 | 对旧能力重要的参数，尽量少改 | 对“哪些参数重要”的估计并不完美 |
| 模块隔离与扩展 | 给新任务增加或选择专门模块 | 模块会增多，也需要可靠路由 |
| 外部记忆与训练结合 | 快速变化的事实留在外部，稳定能力再考虑训练 | 两种存储可能冲突，需要联合评测 |
{{< /codex-table >}}

前几类是持续学习中的经典路线；最后一类是系统组合思路。EWC 的代表性做法，就是限制对旧任务重要的权重变化。普通微调或加一个 LoRA，并不会因此自动获得长期保留能力。[EWC](https://arxiv.org/abs/1612.00796v2)、[持续学习方法分类](https://arxiv.org/html/2404.16789v3)

### SEAL 把学习过程的一部分交给模型

SEAL 让模型根据输入生成用于自身适应的数据与更新指令，再进行参数更新；外层强化学习根据更新后的任务表现，训练它怎样生成更有效的“自我编辑”。这把“从什么材料学习、怎样组织材料”的一部分决策交给了模型。[SEAL](https://arxiv.org/html/2506.10943v1)

但 SEAL 原论文也专门检查了连续更新：随着新材料不断到来，早期任务的表现仍会下降。其训练还依赖可评估的下游任务。它展示了自适应路径，也留下了长期保留和评价信号的问题。[SEAL 的持续更新与局限](https://arxiv.org/html/2506.10943v1#S5)

这一点很关键：**一次成功的自我更新，只证明这次更新有效。持续学习需要一整段时间上的证据。**

## 6 怎样验证 AI 确实少犯了错

“请复述你记住了什么”只能检查它是否能说出来。更有说服力的办法，是在后续任务里观察行为，并与没有这次经验的系统比较。

下面是一套可以从小规模开始的评测设计，不是本文已经运行过的实验。

{{< codex-table label="从记住到学会的行为评测" >}}
| 要检验什么 | 怎样设计任务 | 看什么结果 |
| --- | --- | --- |
| 重复错误是否减少 | 把同一故障机制换个页面、字段名或任务表述 | 同类错误复发率 |
| 能否跨会话保留 | 启动新会话，保留该方法规定的记忆或模型版本 | 无需再次提醒的成功率 |
| 是否理解适用范围 | 混入纯日期、另一项目和不同接口约定 | 错误套用旧经验的比例 |
| 是否发生遗忘 | 更新后重跑旧任务与未相关任务 | 旧能力的退步幅度 |
| 是否值得长期使用 | 在同等预算下比较成功率，或在同等成功率下比较成本 | 调用数、延迟、费用、人工纠正次数 |
{{< /codex-table >}}

可以先比较三组：没有经验、直接带入历史记录、使用整理后的经验。固定基础模型与任务预算，在多种表述、时间间隔和任务顺序下重复运行。这样才更容易判断，收益来自经验组织，还是来自更多上下文和更多重试。

这里的“同类错误复发率”，分母应是**后续确实遇到该规则适用场景的次数**，不能用全部任务数稀释。新任务做得更好，也应同时报告旧任务是否退步。

### 现有基准已经在追问经验的价值

LongMemEval 的原始版本评测信息提取、跨会话推理、时间推理、知识更新与不知道时能否拒答。它提醒我们，记忆的正确性包含“现在还成立吗”。[LongMemEval，ICLR 2025](https://arxiv.org/abs/2410.10813v2)

2026 年的 LongMemEval-V2 更接近“熟悉工作的同事”：它增加了对网页环境状态、操作流程、常见陷阱和错误前提的考查。不过，其核心仍是从历史轨迹中收集证据、回答问题；问答正确不直接等于能在真实环境中执行成功。[LongMemEval-V2，预印本](https://arxiv.org/abs/2605.12493v1)

因此，记忆问答和端到端行动评测最好配合使用。一个检查能否找到经验，一个检查经验是否改变了行动。

<details>
<summary>展开阅读：为什么筛选用例与最终盲测要分开</summary>

开发集可以用来分析失败，验证集可以用来选择候选更新，最终测试集则应独立保留。只要某组题持续影响“哪个版本被留下”，系统就在间接利用它，哪怕模型没有看到题目全文。

Self-Harness 是一个值得留意的例子。其 2026 年预印本在 Terminal-Bench 2.0 的 64 题子集上，用固定模型挖掘失败模式、提出自身执行框架的修改，并通过回归检查筛选。论文报告 Qwen3.5-35B-A3B 的 held-out 通过率由 23.8% 升至 38.1%；方法说明同时明确，该 split 用于自动决定是否采纳候选修改。[Self-Harness 实验设置](https://arxiv.org/html/2606.09498v1#S4)

所以，这组结果支持“通过迭代筛选改善该评测协议下的表现”，不能把它改写成“完全未参与筛选的独立盲测提升”。对于长期系统，还应测试新任务来源、环境变化和成本变化。**held-out 这个名称本身，不足以说明数据在整个优化流程中的角色。**

</details>

## 7 从积累经验走向 RSI

到这里，我们已经有了一条能工作的思路：识别失败，形成经验，改变后续行为，再验证收益。

再往前一步，AI 可以开始处理自己的学习过程。例如，它发现某类经验总被漏检，于是修改检索策略；发现摘要会丢掉条件，于是改变记忆格式；发现验证经常漏掉跨日问题，于是提出更好的测试生成方法。

**当改进后的系统继续参与下一轮自我改进，就出现了递归的结构。** 本文用这个工作定义理解 RSI；不同研究对“自我”和“改进”的边界并不完全一致，实际阅读时仍要看它具体修改了哪一部分。

{{< mermaid >}}
flowchart TD
  A[当前 Agent 及其学习方法] --> B[分析失败和改进瓶颈]
  B --> C[提出记忆 工具 流程或训练修改]
  C --> D[受控实验与独立评测]
  D --> E{收益与回归是否达标}
  E -->|是| F[保留新版本]
  E -->|否| G[保留旧版本与失败证据]
  F -->|参与下一轮改进| A
  G --> B
{{< /mermaid >}}

*递归发生在改进结果重新进入改进过程的位置。图中的独立评测是工程要求，不表示每项研究都已完整实现。*

### 已经出现了哪些具体路径

**Darwin Gödel Machine（DGM）修改 Agent 自己的代码。** 它维护多个 Agent 版本，让候选版本修改自身并接受编码任务评估；底层基础模型保持冻结。论文展示了工具和上下文管理等方面的改进。其外层的档案维护与父代选择过程仍然固定，因此自我修改有明确边界。[DGM](https://arxiv.org/html/2505.22954v2)

**AlphaEvolve 展示了 AI 帮助改善 AI 所依赖的计算过程。** 它结合语言模型生成候选程序与自动评价。DeepMind 在 2025 年的介绍中报告，一项矩阵乘法内核优化使对应内核提速 23%，折算为 Gemini 总训练时间减少 1%。这个例子说明局部优化可以反馈到 AI 研发，但内核提速不能直接等同于模型智能提高，更不能单凭它证明递归加速已经成立。[AlphaEvolve 官方介绍](https://deepmind.google/blog/alphaevolve-a-gemini-powered-coding-agent-for-designing-advanced-algorithms/)

**Memento 3 把外部记忆变成可执行的环境模型。** 这篇 2026 年 10 月的预印本，在冻结语言模型的条件下维护自然语言规则手册，将其编译成预测和规划用的代码；新的观察暴露预测错误后，再修订规则并做轨迹回放验证。更新后的环境模型又影响下一轮探索，因此作者将其讨论为一条基于模型的 RSI 路径。[Memento 3](https://arxiv.org/html/2610.11794v1)

其中的“模型”主要指 Agent 学到的环境规则与可执行表示，并不意味着它重训了底层 LLM。论文在公开游戏和 Pong 案例上报告结果；通过已见轨迹的回放，也无法唯一确定未见状态下的正确规律。这个边界恰好说明，持续探索与反例验证为什么仍然必要。[Memento 3 的方法与泛化问题](https://arxiv.org/html/2610.11794v1#S1)

### 递归结构不保证越改越快

一个系统可以不断生成新版本，却在同一套评测上过拟合；可以提高成功率，却消耗成倍预算；也可以把错误经验写得越来越完整，导致稳定地犯错。

因此，判断 RSI 的进展，我更关心三个问题：

1. **改进能否累积？** 新版本保留了多少旧收益，换环境后还剩多少？
2. **改进过程是否也变好了？** 相同预算下，能否更快发现有效修改、排除无效修改？
3. **评价依据是否可靠？** 系统优化的是实际任务能力，还是某个容易迎合的分数？

这些是对研究结果的判断标准。已有工作展示了不同范围的反馈循环，距离“长期、开放环境中的稳定递归加速”，还需要与这一强度相匹配的证据。

## 8 让每一次纠正留下可验证的变化

对今天的 Agent 应用，一个务实起点是先处理最常重复的几类错误：保留失败证据，写清适用条件，安排检索触发，把关键经验变成工具与检查，再看后续任务中的复发率。

只有在错误跨任务反复出现、反馈足够可靠、训练收益值得承担成本时，再考虑参数更新。每次更新都应同时检查新能力与旧能力。

Memory 让经验有地方存放；持续学习要求经验在时间中转化为能力；RSI 进一步追问，系统能否改善自己积累能力的方法。三者相互连接，却各自需要不同的验证。

回到开头那句“我会记住”：更让人愿意继续合作的证据，是下一次遇到类似问题时，AI 主动找到了那条规则，检查了适用条件，并把事情做对。

进一步讨论 AI 怎样参与下一代 AI 的研发，可以接着读：[RSI 递归自我改进的技术路线与现实边界]({{< relref "/posts/agent-ai/recursive-self-improvement/index.md" >}})。
