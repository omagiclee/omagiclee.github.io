给模型一份几百万 token 的材料，问题未必是“能否找到某句话”。也可能是：**理解每条记录，再统计所有符合条件的案例；把散落在不同文件里的证据连接起来；输出一份比单次生成上限还长的结果。**

RLM（Recursive Language Models，递归语言模型）的做法是：把完整材料保存在外部环境里，让模型通过程序读取和处理它，必要时调用子模型，最后把结果组合起来。单次模型调用仍有上下文限制，但整个系统可以处理远超这个限制的输入。[作者实现](https://github.com/alexzhang13/rlm)

把 RLM 与 [RSI 递归自我改进]({{< relref "/posts/agent-ai/recursive-self-improvement/index.md" >}}) 连起来看，可以区分两种递归：**RLM 关心怎样组织一次任务的计算，RSI 关心怎样让系统持续改进自身能力。** 两者可以组合，但一次递归调用本身不意味着自我改进。

> **递归与智能系统 · 02** · 资料截至 **2026 年 10 月 23 日**。核心实验采用 Zhang、Kraska、Khattab 的 [RLM 论文 v3](https://arxiv.org/html/2512.24601v3)（2026-05-11）；下文的影像反馈案例为说明机制而构造。

## 1 长上下文的难点在于怎样使用信息

“支持百万 token”说明模型接口能接收多长的输入。它没有直接回答另一个问题：输入变长后，模型还能否完成指定任务？

[Lost in the Middle](https://arxiv.org/abs/2307.03172) 在多文档问答和键值检索实验中发现，相关信息所处的位置会影响效果：位于中间时，模型可能更难利用它。这是特定模型与任务上的历史证据，不能理解成所有模型都有相同的性能曲线。

更进一步，**长度相同，信息处理量也可能完全不同。**

{{< codex-table label="长上下文任务的信息需求" >}}
| 任务 | 读者容易理解的例子 | 答案依赖什么 |
| --- | --- | --- |
| 单点检索 | 找到某份报告的发布日期 | 一个或少数证据片段 |
| 多跳关联 | 找到某项实验使用的数据集，再查其许可 | 多处证据及相互关系 |
| 全量聚合 | 统计所有反馈里有多少条属于噪声问题 | 大量记录逐条理解后的结果 |
| 跨记录配对 | 列出所有满足条件的案例对 | 可能随记录数平方增长的关系集合 |
{{< /codex-table >}}

[OOLONG](https://arxiv.org/abs/2511.02817) 专门考察第三类能力：先理解、分类文本，再回答计数和分布问题。它揭示了普通“海底捞针”测试覆盖不到的难点——找到了几条相关材料，不代表处理了所有应该计入的材料。

这里的“常数、线性、平方”描述的是任务所需的证据或关系处理规模，**不等同于实际算法的时间复杂度**。即便只找一个答案，没有索引时也可能需要扫描全文；配对任务则可能通过分组、索引减少实际计算。

## 2 RLM 把上下文变成程序可以操作的对象

可以把普通调用写成 `answer = LLM(question + context)`。RLM 则在外面包了一层运行时：`answer = RLM(question, context)`。区别藏在这个运行时内部。

Python REPL 是一个能反复执行代码、保留变量的交互环境。完整材料放在其中的 `context` 变量里；根模型先获得问题、环境说明和材料的有限元信息，再决定读哪里、怎样拆分。子调用的结果也可以留在变量中，只有必要的观察返回根模型。[作者原始介绍](https://alexzhang13.github.io/blog/2025/rlm/)

{{< mermaid >}}
flowchart TD
    Q[用户问题与材料元信息] --> R[根模型：决定下一步操作]
    C[完整长材料] --> E[持久 REPL：context 与中间变量]
    R -->|生成代码| E
    E -->|有界的观察结果| R
    E -->|程序构造片段与子问题| S[子模型或子 RLM]
    S -->|结果保存在变量中| E
    R -->|指定最终结果变量| F[运行时返回答案]
    E -->|读取变量值| F
{{< /mermaid >}}

三个设计放在一起，才构成这里讨论的 RLM：

1. **输入可寻址。** 用变量、切片和标识符操作材料，避免每轮都把全文重新塞回根模型。
2. **模型调用可编程。** 子模型是代码里可以调用的函数，能放进循环、条件分支和批处理。
3. **中间结果与输出可外置。** 长列表保留在运行时中，程序可以拼接、校验，再由变量返回最终产物。[官方实现与接口说明](https://github.com/alexzhang13/rlm)

例如，根模型写出一个循环，就能对一百个片段调用模型；它不必亲自在对话里展开一百条完整的任务描述。子模型读取的内容由程序构造，根模型也不需要把所有子结果重新读一遍。

### 递归的是调用结构

这里的递归发生在推理运行时。子模型不会因为被调用而更新权重，也不会自动继承根模型看过的一切；它需要收到自包含的子问题及必要材料。论文中，根模型和子模型甚至可以使用不同型号。

按论文的深度定义，`depth=0` 是保留外部环境、移除子调用的消融；`depth=1` 是根模型调用普通 LLM；更深的设置才允许子 RLM 继续展开。**早期介绍只测一层，v3 已测试到三层**，因此“RLM 只做过一层递归实验”已经过时。[论文 §3.2](https://arxiv.org/html/2512.24601v3#S3.SS2)

### 无限上下文指系统抽象

每一次神经网络调用仍须满足自己的 token 预算。根模型的指令、历史、代码、观察结果和输出预留要共同装进窗口；叶子模型的子问题、片段和输出也一样。

外部材料可以远大于窗口，却仍受内存、存储、执行时间和费用约束。把长输出保存在变量里，解决的是“最终结果必须由根模型一次吐出来”的限制，也不自动保证长结果的一致性。**RLM 将单次输入长度问题，转化成了数据访问与计算调度问题。**

## 3 跟着一次影像反馈分析走完整个流程

假设有一万条影像测试反馈，要求：

> 对比版本 A 和 B，在夜景样本中统计噪声、过度降噪和锐化光晕各出现多少次；保留每项统计对应的记录编号。

“暗部颗粒明显”可能属于噪声；“噪声少了，但纹理被抹掉”可能属于过度降噪。只搜索“噪声”会同时遇到改善描述与问题描述，不能直接拿命中数当结果。

一个合理的 RLM 轨迹可以这样展开：

{{< codex-table label="RLM 分析影像反馈的示意轨迹" >}}
| 步骤 | 根模型或程序做什么 | 留在环境中的结果 |
| --- | --- | --- |
| 探查 | 检查字段、数量、若干样例 | 数据格式与标签规范 |
| 确定范围 | 按已存在的场景、版本字段过滤 | 待分析记录 ID 清单 |
| 语义处理 | 分批调用子模型，判断问题类型 | 每条记录的标签、原文证据 |
| 校验 | 检查漏项、重复 ID、非法标签和引用 | 可合并结果与待重试清单 |
| 汇总 | 用程序按版本与标签分组计数 | 统计表及证据 ID 集合 |
| 回查 | 对歧义项和抽样结果重读原文 | 修正记录和最终报告 |
{{< /codex-table >}}

这个例子里，模型承担自然语言理解，程序承担精确计数。只需把小型统计表交回根模型解释，完整证据清单仍保存在外部变量中。

不过，结构化结果只能让错误更容易被检查。**ID 全覆盖不等于分类正确，引用原文存在也不等于原文支持该标签。** 歧义记录需要额外复核；多标签问题还要明确，同一条记录可能计入多类，分类计数之和不一定等于记录数。

<details>
<summary>展开一个根模型可能生成的处理方案</summary>

以下是机制示意，辅助函数省略实现，不能直接运行。`llm_query` 表示运行时提供的子模型调用；批大小、标签定义和结果结构是这个示例的选择。真实 RLM 可以根据观察修改方案。

```python
# context 已由运行时装载；这里假设场景和版本字段是可信结构化字段。
records = parse_records(context)
target = select(records, scene="night", versions=["A", "B"])
results = []

for batch in token_bounded_batches(target, reserve_for_output=True):
    raw = llm_query(make_label_prompt(
        batch,
        labels=["noise", "over_denoising", "halo"],
        require=["id", "labels", "evidence_quote", "uncertain"],
    ))
    items = parse_and_validate(raw)
    assert exact_id_coverage(items, batch)  # 无漏项、重复或额外 ID
    assert quotes_exist_in_source(items, batch)
    results.extend(items)

review_queue = collect_uncertain_and_sample(results)
# 根模型可根据复核结果重试或细分；最终用程序计算，不让模型心算。
report = aggregate_with_evidence_ids(results, target)
# 完成复核后，由运行时返回 report 变量。
```

对全量计数，不能为省钱任意跳过“看起来不相关”的记录。如果场景标签也需要从自然语言推断，那么它同样属于语义处理环节，必须计算其误差与覆盖率。

</details>

这个流程看起来接近 MapReduce，是正常的：**RLM 可以在运行时选择一个 MapReduce 策略。** 它的灵活性在于还能检查异常、改变分块、重新检索或继续委派。对于已经定义清楚、长期稳定的批量分类任务，直接写固定流水线往往更容易维护；RLM 的价值更可能出现在处理方案需要随问题变化的场景。

## 4 RLM 与其他长上下文方法怎样分工

下面比较常见实现方式，不把某一篇论文的基线当作整个方法家族的能力上限。

{{< codex-table label="长上下文方法与 RLM 的分工" >}}
| 方法 | 主要机制 | 更值得尝试的场景 | 需要关注的边界 |
| --- | --- | --- | --- |
| 直接长上下文 | 把材料交给一次模型调用 | 输入可容纳，任务需整体理解 | 实际任务准确率与推理成本 |
| 常见检索式 RAG | 找出相关片段再生成 | 大型知识库中的局部事实问答 | 召回遗漏、跨文档关系 |
| 滚动摘要或压缩 | 用较短表示承接历史 | 长对话、阶段性工作交接 | 被压掉的细节能否找回 |
| 固定 MapReduce | 预定分块、逐块处理、合并 | 可分解且规则稳定的批处理 | 跨块依赖、边界和合并规则 |
| CodeAct 类 agent | 在循环中生成并执行代码 | 通用工具组合与数据操作 | 输入和观察怎样进入上下文 |
| RLM | 外置输入与状态，程序化调用模型 | 大材料上的动态分解、聚合与回查 | 分解质量、调用预算、结果校验 |
{{< /codex-table >}}

RAG 的原始工作把参数知识与可检索的外部知识结合；CodeAct 将可执行代码用作 agent 的动作接口；MemGPT 更早讨论了不同层级之间的记忆调度。这些分别提供了检索、执行和上下文管理的基础。[RAG](https://arxiv.org/abs/2005.11401)、[CodeAct](https://arxiv.org/abs/2402.01030)、[MemGPT](https://arxiv.org/abs/2310.08560)

RLM 的辨识点在于这些能力怎样连接：**材料本身是可编程对象，子模型调用又是程序里的运算。** “能写 Python”并不自动满足这一点；但一个 coding agent 如果已经支持这些设计，也就与 RLM 高度接近。

RAG 与 RLM 完全可以组合：检索器先缩小候选文档范围，RLM 再对候选材料做多跳分析或逐条抽取。对全量统计，则必须另行保证检索阶段没有漏掉应该计数的记录。检索负责缩小范围，不能凭空提供完整性证明。

## 5 实验支持了哪些结论

先明确实验口径。下表来自 **RLM v3 的 Table 1，GPT-5 组**；RLM 根模型使用 GPT-5，子调用使用 GPT-5-mini。各列按各自指标报告，不能横向相加成一个“综合准确率”。

{{< codex-table label="RLM v3 GPT-5 组的主要实验结果" >}}
| 方法 | CodeQA | BrowseComp+ 1K | OOLONG | OOLONG-Pairs |
| --- | ---: | ---: | ---: | ---: |
| 输入规模 | 23K–4.2M | 6M–11M | 131K | 32K |
| 直接调用模型 | 24.0* | 0.0* | 44.0 | 0.1 |
| CodeAct + BM25 | 22.0* | 51.0 | 38.0 | 24.7 |
| 压缩上下文 agent | 58.0 | 70.5 | 46.0 | 0.1 |
| OpenCode + 上下文外置 | **64.0** | **94.0** | 52.0 | 4.8 |
| RLM depth=0 | 58.0 | 88.0 | 36.0 | 43.9 |
| RLM depth=1 | 62.0 | 91.3 | **56.0** | **58.0** |
{{< /codex-table >}}

输入规模的单位为 token；分数采用论文的 0–100 标度。CodeQA 与 BrowseComp+ 为答对比例，OOLONG 使用其聚合评分，Pairs 为 F1。`*` 表示遇到上下文上限，不能解释成在完整读取输入后推理失败。加粗只比较上表列出的配置。[数据与定义：论文 §3–4](https://arxiv.org/html/2512.24601v3#S4)

### 外置材料本身已经带来收益

OpenCode 外置上下文后，在上表的 CodeQA 和 BrowseComp+ 上超过了 depth=1 RLM。因此，不能把“超过原生窗口”全部归功于递归，也不能从这张表推出 RLM 全面优于 coding agent。

### 语义聚合更能体现子调用的价值

OOLONG 中，外置环境但不做子调用的配置得分是 36.0，加入一层子调用后为 56.0；Pairs 中则从 43.9 提高到 58.0。与“全文太长装不下”相比，这组消融更直接地检验了**把语义处理分散到子调用**的收益。

### 递归深度需要按任务和模型选择

同一张表中，GPT-5 组的 Pairs 从 depth=1 的 58.0 提升到 depth=3 的 76.0；但 Qwen3-Coder 组的 OOLONG 从 depth=1 的 48.0 降到 depth=2 的 26.0。更深的调用树增加了计算机会，也增加了分解、格式和合并出错的机会。[论文 Table 1](https://arxiv.org/html/2512.24601v3#S4)

独立复现 [Think, But Don’t Overthink](https://arxiv.org/html/2603.02615v1#S4) 也观察到深度增加后的退化，以及简单检索任务的显著延迟增长。不过它每个条件只运行一次、每次 20 个样本，并报告了格式导致的评测失败；适合用来发现故障模式，不足以证明深递归普遍无效。

<details>
<summary>展开评测范围与成本，避免误读百万 token 和低成本</summary>

**BrowseComp+ 1K 是受控子设置。** RLM 论文抽取 150 个问题，每题提供 1,000 篇文档，保证答案及支撑证据存在。原始 [BrowseComp-Plus](https://texttron.github.io/BrowseComp-Plus/) 是固定文档库上的深度检索评测；论文中的 91.3 不能当作开放互联网搜索的准确率，也不能直接与完整基准排行榜比较。

**OOLONG 的分数也限定在具体切分。** RLM 使用 `trec_coarse` 的 50 个任务；OOLONG-Pairs 则是作者构造的 20 个配对问题，不能替代整个 OOLONG 的结果。

**更强不保证更便宜。** 论文报告的每题平均 API 成本，单位为美元：

| 任务 | 对照方法 | 对照成本 | RLM depth=1 |
| --- | --- | ---: | ---: |
| CodeQA | 直接调用 | 0.13 ± 0.07 | 0.11 ± 0.10 |
| OOLONG | 直接调用 | 0.14 ± 0.02 | 0.43 ± 0.85 |
| BrowseComp+ 1K | 压缩 agent | 0.57 ± 0.10 | 0.99 ± 1.22 |

`±` 是论文报告的标准差；价格按论文实验时的提供商计费，不是当前报价。CodeQA 的直接调用还受到窗口限制，因此这组费用不构成同等完成质量的价格比较。GPT-5 组的压缩 agent 使用 GPT-5-nano 做压缩、GPT-5 作答，也不是所有阶段都使用同一个模型。

论文的主实验实现采用阻塞、顺序式模型调用；仓库后续已经提供批量并行接口。旧实验延迟与当前实现能力应分开理解。正式评估还应记录端到端耗时、P95、失败重试与环境费用。[论文成本与运行时间说明](https://arxiv.org/html/2512.24601v3#S4)、[当前实现](https://github.com/alexzhang13/rlm)

</details>

## 6 工程上最重要的是约束计算与保留证据

RLM 没有消除信息处理工作。如果一万条记录都需要语义分类，就仍要覆盖一万条记录；更小的片段可能提高局部可靠性，却也会引入重复提示词、更多请求和合并开销。

可以用一个简单账本理解费用：**根模型各轮费用 + 全部子调用费用 + 检索与执行环境费用**。调用树有多少分支、多少次重试、多少层依赖，往往比“输入总共几百万 token”更能解释实际成本。

下面是本文建议的实现检查项：

{{< codex-table label="RLM 的故障与工程处理" >}}
| 故障 | 典型后果 | 实现时的处理方式 |
| --- | --- | --- |
| 分块切断依赖 | 代词、定义或条件失去来源 | 按语义边界切分，传递共享定义；重叠块按 ID 去重 |
| 子模型输出不完整 | 计数偏低、配对遗漏 | 校验覆盖范围、结构和来源，再决定重试 |
| 合并只剩摘要 | 结论失去可核查证据 | 保存记录 ID、原文位置和标签依据 |
| 调用失控 | 延迟与费用长尾 | 深度、调用数、token、时间及并发分别设限 |
| 观察结果不断增长 | 根模型窗口仍然溢出 | 限制打印量，以变量引用长结果，管理历史 |
| 不可信材料影响代码 | 执行意外操作或访问无关数据 | 将材料视为数据，在隔离环境执行并限制权限 |
{{< /codex-table >}}

最后一项尤其具体：作者仓库默认的 `local` REPL 在宿主进程中执行 Python，文档明确区分它与隔离环境。变量命名空间的限制不能替代操作系统层面的隔离。[官方环境说明](https://github.com/alexzhang13/rlm#repl-environments)

做第一轮实验时，建议同时保留四个对照：直接长上下文、检索或固定分块流水线、只有外置环境的 agent、允许子调用的 RLM。保持材料、输出要求和预算可比，再看准确率、证据覆盖率、总费用与延迟。这样才能知道收益来自哪里，以及是否值得引入更复杂的控制流程。

## 7 后续研究把重点推向训练和运行时

RLM 最初可以通过提示词包在现成模型外面。后续研究则开始追问：模型怎样学会更合适地拆任务？运行时能否减少无效递归？

{{< codex-table label="RLM 的后续研究方向" >}}
| 方向与时间 | 具体进展 | 阅读时保留的边界 |
| --- | --- | --- |
| 受约束的控制流，2026-03 | λ-RLM 用带类型的函数组合子组织拆分、映射与合并 | 终止与成本保证依赖其运行时及假设，不等于语义答案正确 |
| 学习调度，2026-05 | RLM v3 加入 Qwen3-8B 训练；alphaXiv 探索共享父子策略的 4B 模型 RL | 训练协议与评测任务不同，不能混合成一个通用提升数字 |
| 持续运行的 agent，2026-08 | Prime Agent 将 RLM 式 IPython 环境与跨轨迹历史、记忆、技能结合 | 技术报告的系统包含多种组件，整体收益不能全归因于递归 |
| 长视频，2026-10 | RVLSM 按语义场景分解视频，并调用 VideoLLM 与多模态工具 | 新的在审预印本；已报告的是视频摘要任务 |
{{< /codex-table >}}

对应原始资料：[λ-RLM](https://arxiv.org/html/2603.20105v1)、[RLM v3 训练实验](https://arxiv.org/html/2512.24601v3#A1)、[alphaXiv 训练报告](https://www.alphaxiv.org/blog/reinforcement-learning-for-rlms)、[Prime Agent 技术报告](https://arxiv.org/abs/2608.23552)、[RVLSM 预印本](https://arxiv.org/abs/2610.26431)。

其中，alphaXiv 的实验让父模型与子模型共享策略，在科学文献证据选择任务上训练；它提示我们，“会回答问题”与“会安排怎样读材料”可以分别成为学习目标。这个实验并不证明小模型已经具备同等级的通用能力。

从这些工作可以提出一个工程判断：**长上下文系统的性能，越来越需要连同模型、数据访问方式和运行时一起评估。** 同一个模型，换一套拆分、调用与校验方法，可能就会表现出完全不同的有效处理范围。

## 8 与 RSI 的连接在于两个不同的循环

RSI（Recursive Self-Improvement，递归自我改进）要求改进作用于系统自身，并影响后续产生改进的能力。作为相关的实证探索，[Darwin Gödel Machine](https://arxiv.org/abs/2505.22954) 修改 agent 自身代码，并通过编码基准选择候选版本；这与把一道题拆给多个模型处理，有不同的评价对象。

{{< mermaid >}}
flowchart TD
    subgraph I[任务内的 RLM 循环]
      A[问题与外部材料] --> B[分解 调用 合并 校验]
      B --> C[本次任务结果]
    end
    subgraph O[面向能力改进的外层循环]
      D[分析失败轨迹] --> E[提出模型或运行时改动]
      E --> F[独立评测与回归检查]
      F --> G[保留通过检验的新版本]
      G --> D
    end
    C -.提供经验.-> D
    G -.改变后续任务系统.-> A
{{< /mermaid >}}

图中组合是一种系统设计思路。内层判断“这次任务完成得怎样”，外层判断“新版本是否在未参与改进的任务上更强”。只有把改动、验证和后续能力连接起来，才开始触及自我改进问题。

这也说明，把 RLM 训练得更会分解任务，并不自动构成 RSI：训练过程可能完全由人设计，收益也可能局限于某个任务。持续保存记忆同样不等于持续提升能力。

对超长上下文应用，RLM 给出的实用启发很明确：**把有限的模型窗口留给当前需要的语义判断，把大规模材料、精确运算与可追溯状态交给程序管理。** 当问题可以被可靠地拆分和合并，这种组织方式就有机会把额外推理计算转化为更大的有效上下文。
