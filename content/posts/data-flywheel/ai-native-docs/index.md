「给样本列表加一个日期筛选。」如果一条样本 11 月 23 日采集、24 日才入库，运营选 24 日时，该不该看到它？

假设运营想核对 24 日入库的样本，而后端的 AI 从已有字段里选了采集时间。前端的日期控件能用，后端的单测也能过，页面却拿不到运营要查的样本。换一位同事接手，他还得找人确认当时讨论的是哪个日期，以及已有测试究竟验证了什么。

在多人使用 AI 开发的数据飞轮平台上，我希望接手的人拿到一个需求编号，就能回答三个问题。**用户要完成什么操作？团队确认过哪些规则？当前版本有哪些可复核的验收结果？** 日期筛选是个小例子，足够看清这三件事怎样贯穿一次变更。

<!--more-->

## 先把用户要解决的问题说清楚

以运营核对入库批次为例。现有列表可以按处理状态筛选，但运营在核对某天的入库情况时，还要在跨天的结果里逐条核对时间。这个场景给出了筛选要服务的任务，也解释了为什么查询依据应该是入库日期。

接下来要把「按日期查」补成开发和验收都用得上的要求。日期的含义由熟悉工作场景的人确认。AI 可以拿着实际数据举反例、查现有行为、列出待确认项，帮助团队尽早发现分歧。

{{< codex-table label="开工前需要确认的业务问题" compact="true" >}}
| 先问什么 | 这个示例中的决定 |
| :--- | :--- |
| 谁在什么场景下使用？ | 运营需要在样本列表里核对指定日期范围内入库的样本。 |
| 一个日期对应哪个事件？ | 看入库时间。一条 23 日采集、24 日入库的样本，应在 24 日的结果里。 |
| 一天从什么时候开始？ | 按上海时区计算。起始日和结束日当天都计入，允许只查同一天。 |
| 怎样与现有列表配合？ | 日期可留空。填写时，与状态等现有条件一起筛选，列表和分页总数采用同一口径。 |
| 本次交付覆盖哪里？ | 范围是样本列表。按采集日期查询和导出调整另行评估。 |
{{< /codex-table >}}

还要查清现状。比如同名字段到底在入库成功时写入，还是记录了样本创建时间。AI 可以沿数据模型、写入流程和列表接口定位依据，并注明是读源码得到的结论，还是用数据验证过的行为。如果历史样本缺少入库时间，这会直接影响运营看到的结果，应先确认这些样本在选中日期范围时怎样处理。

### 用具体结果确认需求

把决定和验收条件放进一页规格。下面的样本和结果是演示用例，可在真实项目中换成可复现的测试数据。

{{< codex-table label="样本列表日期筛选的验收条件" >}}
| 验收条件 | 应看到的结果 |
| :--- | :--- |
| **AC-01 日期含义** | 样本 A 是 23 日采集、24 日入库，B 是 24 日采集、25 日入库。选 24 日，返回 A，不返回 B。 |
| **AC-02 同日与零点** | 起止都选 24 日。当日零点和当日晚间入库的样本计入，24 日前和 25 日零点起入库的样本排除。 |
| **AC-03 组合筛选** | 同时选日期和「已处理」，返回满足两项条件的样本，分页总数也是交集的总数。清空日期后，恢复仅按状态筛选。 |
| **AC-04 无效输入** | 缺少起止日期的一端、日期无效或起始晚于结束时，应提示修正。起止都留空时保留原列表行为。 |
{{< /codex-table >}}

AC-01 要核对**样本 ID**。按入库日和按采集日都可能返回一条记录，只数条数会漏掉这个错误。同理，如果后来把上海时区改为按用户时区计算，就要更新边界用例，并提醒正在按旧规格工作的人重新验证。

## 用同一份规格落实开发和验收

**规格驱动开发（Spec-Driven Development，SDD）在这里的作用，是让需求确认后的同一份规格同时约束设计、实现和验收。** AI 可以参与每一步。业务负责人确认行为，开发者确认接口和实现取舍，审查者根据规格复核结果。聊天里的决定进入团队可访问的记录后，新会话就有了共同依据。

**设计接口。** 前端传起止日历日期，例如 `2026-11-24`。服务端按上海时区取起始日零点和结束日的次日零点，转为数据库使用的时间基准后查询，包含下界、排除上界。这样能覆盖结束日当天的所有时间精度。参数名和错误格式按现有接口约定确定。设计记录保留这个取舍，接口文档维护调用方式。

**分工实现。** 前后端确认接口后可并行。前端用模拟数据完成日期选择、输入提示和重置行为，后端实现查询和分页，测试准备能区分采集日与入库日的样本。如果某条业务规则变化，负责人更新共享规格和受影响的任务，各会话再基于新版本继续。分支、共享文件的负责人和合并顺序仍由团队协调。

**审查和交付。** 审查者从已确认的规格和被测提交出发，检查真实接口是否返回 A，以及零点两侧和无效参数的行为。再用连着真实接口的页面执行 AC-03，核对筛选结果和分页总数。PR 关联验收用例、被测提交、测试环境和结果。模拟数据验证过的界面可以先记录，真实链路仍需单独验收。

## 让下一位同事从需求编号接着做

接手人首先要知道**这次改什么、做到哪一步**。维护模块的人则需要知道**已上线的系统现在怎样工作**。我会用一页变更说明把本次调研、规格、设计和验收串起来，再把对后续需求有用的行为和决定沉淀到长期文档。

{{< codex-table label="团队需要到哪里找信息" compact="true" >}}
| 想找什么 | 放在哪里 |
| :--- | :--- |
| 谁负责、这次做到哪了 | 工单维护负责人、优先级和状态，并链接已确认的规格版本。 |
| 为什么改、怎么改、验证了什么 | `docs/changes/DF-042-date-filter/index.md` 保留变更说明，链接调研依据、接口定义、PR、测试运行和发布记录。 |
| 现在可以依赖哪些规则 | `docs/domains/` 维护已生效的业务行为。接口字段和错误定义引用仓库的接口契约。 |
| 为什么做了某个跨版本的技术选择 | `docs/architecture/` 保留设计取舍。需要跨团队讨论时用 RFC，确认后用 ADR 记录理由。 |
| 新人或新 AI 会话怎么上手 | `README.md` 给人看，`AGENTS.md` 放常用项目约定和验证入口，`docs/index.md` 帮助两者定位详细资料。 |
| 需要按任务读取的 AI 协作规则 | `docs/engineering/ai/` 维护调研取证、并行分工、审查和交接的细则与示例。 |
{{< /codex-table >}}

小需求可以只用一页。跨模块变更再按需拆出调研、设计、计划和验证页面，保持从同一个需求入口能找到。上线后，把日期字段的业务含义和时区补进样本筛选的领域说明，有灰度限制就一起写明。可复用的操作步骤放进 `docs/guides/`，排障和恢复放进 `docs/runbooks/`。

这些方法可以同时用。Docs as Code 用 Git 和 PR 管理文档版本，Diátaxis 帮助按读者任务区分教程、操作指南、参考和原理说明，RFC 与 ADR 分别服务于提案讨论和决策记录。SDD 把同一份行为规格用到开发和验收。 [Backstage TechDocs](https://backstage.io/docs/features/techdocs/) · [Diátaxis](https://diataxis.fr/) · [Rust RFC](https://rust-lang.github.io/rfcs/) · [ADR](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)

## 先用现有流程试一遍，再决定工具 {#sdd-tool-selection}

对已有的数据飞轮平台，我会先用**一个工单、一页规格和现有 PR**跑完日期筛选。让一位没参与讨论的同事，在新会话里只凭工单找到已确认的版本、复跑一个验收场景。再看联调时还有哪些业务口径才第一次被提起，接手人追问了什么，以及验收证据能不能复现。文案类小改动可直接在工单写清预期。

SDD 是一种工作方法，下表是几个有公开文档的代表性实现。它们的能力可以从官方文档核对，行业采用率和在本团队的效果仍需各自的证据。ESEM 2026 的一项研究分析了 119 个开源仓库的 88,052 个 PR，匹配风险后未发现带规格记录的 PR 引入缺陷的比例有显著差异。样本里的记录主要是工单引用，研究没有直接评估下表工具。 [ESEM 2026 论文](https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.ESEM.2026.84)

{{< codex-table label="按团队遇到的卡点选择 SDD 工具" >}}
| 反复遇到的问题 | 可以试的工具与理由 |
| :--- | :--- |
| 已有平台持续迭代，大家常搞不清正在改的规格和当前有效的规格 | **OpenSpec** 按变更组织提案、规格和任务，归档时把已交付的变更纳入现行规格。 [官方快速入门](https://openspec.dev/docs/quickstart) |
| 团队使用不同编码 Agent，计划、任务或最终检查经常漏项 | **GitHub Spec Kit** 提供从规格、计划、任务到实施和收敛检查的流程，可接入不同编码 Agent。 [官方文档](https://github.github.io/spec-kit/) |
| 团队希望在集成工具中一起评审需求、技术设计和任务 | **Kiro Specs** 提供从需求开始的功能规格流程，可以在 Kiro 中逐阶段评审和执行。 [官方文档](https://kiro.dev/docs/specs/) |
| 产品方向、范围和架构都需要讨论，一次开发会话很难定下来 | **BMad Method** 提供澄清、规划、构建和验证的流程，可按变更大小选择路径。 [官方文档](https://docs.bmad-method.org/start/how-bmad-works/) |
{{< /codex-table >}}

试点跑完后，选型依据就具体了。上线后的行为规则反复失同步，我会先试 OpenSpec。多个 Agent 反复漏掉任务拆分或验收，我会先试 Spec Kit。若新同事已经能凭工单接手并通过可复现的验收，现有流程就足以支撑这类改动。
