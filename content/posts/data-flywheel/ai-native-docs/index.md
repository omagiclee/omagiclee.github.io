「给样本列表加一个日期筛选。」在数据平台里，这是个很普通的需求。前端同事让 AI 加了日期选择器，后端同事让 AI 按采集时间查数据。两边单测都过了。联调时才发现：运营想查的是**哪天入库**，不是哪天采集。一条 11 月 23 日采集、11 月 24 日入库的样本，选 24 日应该能查到，页面却没显示。

就算把字段改对，还有两个问题：**按哪个时区算一天？结束日期当天算不算？** 这些问题不必写成长篇方案，但答案也不能只留在某个人的 AI 会话里。

**这正是规格驱动开发（SDD）能解决的那部分问题：让不同人、不同 AI 会话按同一份已确认的行为规格开发，再用它验收。** 对日期筛选，一页规格就够，不必先装框架。

<!--more-->

## SDD 解决的是「各做各的」，不只是「文档怎么摆」

**判断有没有用上 SDD，不看目录里有没有 `spec.md`，看规格有没有改变开发和验收的做法。** 如果代码写完才补上「已支持日期筛选」，那是事后记录。如果前后端开工前就按「入库日期、上海时区、结束日计入」分工，审查时还用同一条规格检查实际结果，这才是这里说的 SDD。

{{< codex-table label="多人用 AI 开发：问题和对应做法" compact="true" >}}
| 团队碰到的问题 | 用什么解决 |
| :--- | :--- |
| 不同会话各自解释「日期」 | **SDD：**需求负责人确认一份规格；前后端按它落实接口，测试按它准备样本。 |
| 各自单测都过了，联调结果却不对 | **SDD + 测试：**从规格写出共同的验收用例；用真实接口检验返回的样本，而不是各自验证自己的假设。 |
| 换人或换个 AI 就找不到决定和进度 | **仓库文档 + 交接：**工单链接到已确认的规格版本；PR 和 CI 留下做了什么、测了什么。SDD 提供共同依据，不能自动同步会话。 |
| 两个人改同一段查询、接口同时演进 | **并行协作规则：**明确谁负责哪段改动，约定接口兼容和合并顺序。规格一致也不代表没有代码冲突。 |
{{< /codex-table >}}

SDD 也不会替业务决定是「入库」还是「采集」。如果团队还没定，规格应标明待确认，不能让 AI 把猜测当成决定。**文档解决「到哪找」，SDD 解决「按什么做、怎么证明做对」，分工和发布仍走已有工程流程。**

## 先按读者要找的东西分目录

接一个需求的人想知道「现在做到哪了」，维护模块的人想知道「当前规则是什么」。如果把需求、调研、方案和审查分别塞进四个全局目录，接手人就得去四处拼故事。更自然的做法是：**把同一次变更放在一起，再为跨版本仍有用的知识留一个固定位置。**

```text
repo/
├── README.md                         # 项目是什么，怎么启动
├── AGENTS.md                         # 给编码 Agent 的短入口
└── docs/
    ├── index.md                      # 文档地图：按需求、领域或任务找
    ├── changes/
    │   └── DF-042-date-filter/
    │       └── index.md              # 本次改动：范围、规则、分工、验收和交接
    ├── domains/                      # 数据集、流水线、算子、筛选与评测
    ├── architecture/                 # 系统边界、架构图、重要决定
    ├── guides/                       # 比如怎样注册一个新算子
    ├── runbooks/                     # 比如怎样定位失败、恢复和回滚
    └── engineering/
        ├── testing.md                # 测试与发布验证规则
        └── ai/                       # AI 协作手册与交接模板
```

**变更包**就是 `changes/` 下某个需求的记录。本例只有 `index.md`。复杂需求再按需要拆出 `spec.md`、`research.md`、`design.md`、`plan.md` 或 `verification.md`。工单继续管负责人、优先级和进度；代码审查的讨论留在 PR；变更包用链接串起这些记录，不另外维护一套进度表。如果一个需求跨多个仓库，选一处存放变更包，各仓的 PR 都回链同一需求编号。

**长期文档**回答的是「现在怎样」。例如，样本筛选的领域说明维护已上线的筛选行为，正在开发的日期筛选先留在这次变更里。接口字段以仓库里的接口定义为准，不在 Markdown 里再抄一遍。只有日后仍会被问「当初为什么这么选」的决定，才值得补架构决策记录（ADR）；跨团队还有分歧的方案，可以先用提案（RFC）讨论。

这些做法可以组合，不必选边站。[Docs as Code](https://backstage.io/docs/features/techdocs/) 解决的是怎样用 Git 和 PR 管文档版本；[Diátaxis](https://diataxis.fr/) 解决的是怎样区分教程、操作指南、参考和原理说明；[RFC](https://rust-lang.github.io/rfcs/) 和 [ADR](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions) 分别用于讨论提案和保留决定。它们都不要求把同一需求拆到不同地方。

## 走一遍：样本列表新增日期筛选

### 一页规格：把「按日期查」写成可验收的行为

以下是可以直接写进 `DF-042-date-filter/index.md` 的示例。字段和时区是这个例子里的决定，不是所有平台都该照搬的默认值。

{{< admonition type=info title="DF-042 · 样本列表按入库日期筛选" >}}
**目标：**运营可以查某天或一段日期内入库的样本。只改样本列表，本次不改导出，也不新增按采集日期筛选。

**规则：**按入库时间筛选，以 `Asia/Shanghai` 为准，起止日期当天都计入。日期可不填；填了就与现有筛选取交集，先筛选再分页。
{{< /admonition >}}

{{< codex-table label="日期筛选的验收用例" compact="true" >}}
| 用例 | 怎么验收 |
| :--- | :--- |
| **AC-01 · 字段选对** | 11 月 23 日采集、24 日入库的样本，选 24 日能查到；选 23 日查不到。 |
| **AC-02 · 边界正确** | 选 24 日到 24 日：24 日 `00:00` 和 `23:59:59.999` 都计入；23 日 `23:59:59.999` 和 25 日 `00:00` 都排除。 |
| **AC-03 · 与现有筛选共存** | 同时选状态和日期，只返回同时满足的样本，分页总数也按交集计算；清空日期后恢复为仅按状态筛选。 |
{{< /codex-table >}}

AI 可以起草这些条目，但由需求负责人确认「入库」和「按上海时区计算」是不是业务想要的。确认后把工单指向可定位的规格版本，例如带提交号的链接。若后来决定支持用户时区，先更新规格、接口和受影响的验收用例，通知已经开工的人；按旧规格通过的边界测试不能当成新规则的证据。

### 先对齐接口，再让各自的 AI 并行做

后端先核对现有时间字段和列表接口，再与前端约定：页面传 `YYYY-MM-DD` 的起止日期，**要么都不传，要么都传**；缺一端、日期无效或起始晚于结束，接口按现有参数错误约定返回。参数名和错误格式以仓库里的接口定义为准，变更页只链接，不再抄一遍。

例如用户选择 11 月 24 日，服务端把上海时间的当日零点和次日零点转成数据库使用的时间基准，再按「`>= 起始日零点` 且 `< 结束日次日零点`」查询。这样不用把结束时间凑成 `23:59:59`，也不会漏掉该秒之后的毫秒数据。前端直接按日历日期提交，不再自行转成 UTC 时间戳。

前端可以按契约先用模拟数据开发，后端实现查询，测试同步准备「采集日和入库日不同」以及「正好落在零点」的样本。并行的是实现，**不是各自定义日期的含义**。

### Review 回到规格，发布后再更新长期说明

审查者可以用自己的 AI 直接读规格、改动和测试，不以实现者的总结为结论。比如 AC-01 准备两条样本：A 是 23 日采集、24 日入库，B 是 24 日采集、25 日入库。选 24 日时，按采集日会返回 B，按入库日会返回 A，**结果都是一条，只数条数发现不了问题**。再按 AC-02 测边界、按 AC-03 检查组合筛选和分页。在 PR 或变更页关联验收用例、被测提交、环境和测试链接；没测的就写「未验证」。

代码合并后，变更包仍保留当时怎么做、测了什么。等功能上线，把「样本列表按入库日筛选、日期按哪个时区解释」补进样本筛选的领域说明；还在灰度就注明启用条件。不必为了这次小改动新建运维手册。**变更包记这次发生了什么，长期文档告诉下一位读者现在可以依赖什么。**

## AI 规则怎么放，换人时怎么接

`AGENTS.md` 不必解释整个项目。它只放新会话每次都该知道的内容：从哪里找文档，按什么方式找到本次需求，用哪些入口构建和测试。AI 专用但不需要每次重读的规则，放进 `docs/engineering/ai/`，例如：

- **调研：**区分已从源码确认的行为、实验结果和待核实的猜测。
- **协作：**按需求或任务分支工作；共享接口变了，要通知依赖它的人，而不只是改自己的文档。
- **审查：**按验收条件复核，注明哪些没有运行、没有覆盖或仍待确认。

把这些规则按任务链接起来就够了。能用 CI 检查的事，例如链接是否失效、回归是否通过，交给 CI；不要让团队靠记住一长串提示词来维持一致性。[AGENTS.md](https://agents.md/) 提供的是约定俗成的入口，[OpenAI 的工程案例](https://openai.com/index/harness-engineering/) 则展示了短入口、版本化知识和自动检查如何配合。

真正交接时不必粘贴整段聊天。下面这种记录放在变更包首页，读起来更接近一条同事留言：

> **DF-042 · 样本列表新增日期筛选（交接示例）**
>
> - **从哪开始：**读已确认的规格版本，再看后端 PR 和被测提交。
> - **已经验证：**API 按入库日筛选，两个零点边界正确（AC-01、AC-02）。
> - **还没验证：**页面接真实 API 后，状态与日期组合筛选的结果和分页总数（AC-03）。
> - **下一步：**用测试数据从页面跑一次 AC-03，把结果和被测版本补到这页。

正式使用时，给规格、PR、被测提交和测试运行加上链接。未合入的资料可以放在团队有权访问的草稿 PR 里，标明哪些是讨论稿、哪一版已确认可用于开发。接手同事开一个新会话，只需要说：「接手 DF-042，按交接页链接的规格版本验收 AC-03；如果接口和规格对不上，先指出分歧，不要按当前代码改写验收口径。」

## 先试一页规格，什么时候才需要 SDD 工具？ {#sdd-tool-selection}

对已有的数据平台，我会先用现有 Agent、工单和 PR 跑一次：**工单链接已确认的一页规格，前后端用同一个版本开工，PR 给出对应验收证据。** 再找一位没参与讨论的同事，只给工单，看看他能否在新会话找到正确规格并跑完 AC-03。若只是改按钮文案，直接在工单写清预期即可，不必另建文件。

不要用新增文件数判断效果。[一项 2026 年开源 PR 研究](https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.ESEM.2026.84) 未发现样本中有规格相关记录的改动缺陷更少；样本主要是工单引用，并未直接检验下表的工具。试点时更值得看的是：有多少口径分歧要到联调才发现，接手人还要追问什么，验收能否复跑。再看卡点是否值得用工具解决：

{{< codex-table label="SDD 工具与适用场景" >}}
| 选项 | 什么时候值得用 |
| :--- | :--- |
| [OpenSpec](https://openspec.dev/docs/quickstart) | 已有系统改动多，常搞不清正在做的变更和当前有效的规格。它把两者分开，归档变更时再更新规格。 |
| [GitHub Spec Kit](https://github.github.io/spec-kit/) | 大家使用不同 Agent，想共用从规格、计划、任务到实现和检查的流程，而不是各写各的。 |
| [Kiro Specs](https://kiro.dev/docs/specs/) | 团队愿意使用集成开发环境，希望在同一个界面写需求、审方案、拆任务和执行。 |
| [BMad Method](https://docs.bmad-method.org/start/how-bmad-works/) | 需求还不明朗，需要先做产品判断、架构设计和交付拆分。问题已经清楚的小改动，不必走完整流程。 |
{{< /codex-table >}}

如果轻量做法已经能减少联调返工，就不必引入工具。如果反复漏掉的是「上线后更新现行规格」，先看 OpenSpec；如果反复漏掉的是「不同 Agent 交付时少了任务拆分或验证」，先看 Spec Kit。**先修复真实发生的协作问题，再决定要不要增加流程。**
