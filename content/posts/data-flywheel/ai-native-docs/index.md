几位同事各自带着 AI 开发同一个数据飞轮平台。一个会话刚确定流水线失败后应该怎么恢复，另一个已经按旧假设写好前端，第三个开始 Review，却不知道哪一版需求生效。此时多生成几份 Markdown 也没用，甚至会让人更难找到答案。

我的建议是：**用一个变更包串起一项需求，用领域文档说明平台现在怎么工作，用 AI 协作手册说明团队怎么工作。根 `AGENTS.md` 只放入口和每次都要遵守的约定。** 代码和文档都可以由 AI 起草、实现和验证；是否采纳一个决定、是否符合验收、是否已发布，则以明确的决定和可查的证据为准。

本文接续[生产级数据平台的 AI 开发工作流]({{< relref "/posts/vibe-coding/production-data-platform-ai-workflow/index.md" >}})，具体讨论仓库怎么组织。文中的需求编号、目录和证据都是设计示例，不代表实际平台已采用这套体系。公开资料核对于 **2026-11-24**。

<!--more-->

## 1 几种常见方案各管什么

这些做法不在同一层。Git 管的是谁改了哪一版，Diátaxis 管的是读者怎么找，规格驱动开发（SDD）管的是一个需求怎样变成可验证的改动。

{{< codex-table label="常见文档与规格驱动方案对比" >}}
| 方案 | 主要解决什么 | 我会怎样用 |
| :--- | :--- | :--- |
| Docs as Code · [Backstage TechDocs](https://backstage.io/docs/features/techdocs/) | 文档与代码共同版本化，用 Git、PR 和 CI 管理；文档站是展示入口 | 工程知识和对应代码一起审查。排期继续用工单，不必先建文档站 |
| [Diátaxis](https://diataxis.fr/) | 按阅读目的区分教程、操作指南、参考和原理解释 | 用来设计长期阅读入口，不把一项需求拆散到四个目录 |
| [Rust RFC](https://rust-lang.github.io/rfcs/) / [Nygard ADR](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions) | RFC 征询重大变更的意见；ADR 记录架构决定、背景与后果 | 常规设计放变更包；跨团队讨论用 RFC，日后仍会被问「为什么这样做」的决定留 ADR |
| [GitHub Spec Kit](https://github.github.com/spec-kit/) | 把规格、计划、任务、实现与一致性检查串起来 | 团队需要统一 AI 工作入口时试用；小改动不必走完整功能流程 |
| [OpenSpec](https://github.com/Fission-AI/OpenSpec) | 用独立目录承载提案、规格增量、设计和任务，收尾时归档并更新规格 | 借鉴「进行中的变更」和「当前有效规格」分开的做法，适合已有系统迭代 |
| [OpenAI 的 Harness Engineering 案例](https://openai.com/index/harness-engineering/) | 让 Agent 从短入口逐层查看知识，让计划与决定可版本化，并用 CI 检查文档漂移 | 参考其上下文导航与机械检查，不照搬案例团队的目录或合并策略 |
{{< /codex-table >}}

我会先保留现有的 Git 和工单系统，用 **Docs as Code + 按变更组织 + 按领域沉淀** 开始。若团队反复需要 AI 创建同一套产物，再考虑引入工具；具体区别见[第 7 节：SDD 是什么，工具怎么选](#sdd-tool-selection)。

## 2 目录：一条按变更找，一条按领域找

```text
repo/
├── AGENTS.md
├── README.md
└── docs/
    ├── index.md
    ├── changes/
    │   └── DF-042-resumable-pipeline/
    │       ├── index.md
    │       ├── spec.md
    │       ├── research.md
    │       ├── design.md
    │       ├── plan.md
    │       └── verification.md
    ├── domains/
    │   ├── index.md
    │   ├── datasets/              # 数据集、样本、快照、血缘
    │   ├── pipelines/             # 编排、运行状态、恢复
    │   ├── operators/             # 算子、参数、输入输出、版本
    │   ├── curation/              # 检索、筛选、标注、审核
    │   └── evaluation/            # 评测口径、基准集、反馈
    ├── architecture/
    │   ├── overview.md
    │   └── decisions/             # ADR
    ├── guides/                    # 接入、使用、常用开发操作
    ├── runbooks/                  # 值班、故障定位、灰度与回滚
    └── engineering/
        ├── ai/                    # AI 协作规程与模板
        └── testing.md             # 人与 AI 共用的验证规范
```

{{< codex-table label="项目文档各目录的职责" >}}
| 位置 | 放什么 | 谁来维护 |
| :--- | :--- | :--- |
| `docs/index.md` | 项目地图：按需求编号、业务领域、开发或运维任务找到入口。不维护手抄的进度总表 | 项目维护人 |
| `changes/` | 为什么改、查了什么、怎么改、验证了什么；完成后在原路径保留历史，工单指向它 | 变更负责人 |
| `domains/` | 当前有效的业务规则。比如流水线运行状态、数据集快照何时不可变、算子怎样识别版本 | 领域负责人 |
| `architecture/` | 跨领域边界、依赖方向、部署拓扑和长期取舍。过时的 ADR 标明被哪一条替代 | 相关模块维护人 |
| `guides/`、`runbooks/` | 怎样注册算子；运行卡住时怎样辨认、恢复、回滚。前者支持日常任务，后者注明实际操作的环境条件 | 流程维护人 |
| `engineering/` | 工程流程、测试、Review 与 AI 协作规范；配置或脚本能执行的规则不要只写在文档里 | 工程流程维护人 |
{{< /codex-table >}}

如果平台拆为多个仓库，每个领域仍由拥有实现或契约的仓库维护。跨仓变更选一个协调仓库保存唯一变更包，前端、服务和算子仓的 PR 都回链同一个 ID，并标清兼容版本和合入顺序。

**不用同时建 `requirements/`、`research/`、`design/`、`reviews/` 四套全局目录。** 换人时通常是接一个需求，不是阅读所有调研。跨需求会反复用到的比较才提炼到相关领域，长久有效的决定才提炼成 ADR，逐行 Review 留在 PR 里。历史留在变更包，长期知识写在它的主维护位置，两者互相链接，不相互复制。

## 3 一个变更包怎样走完交付

以 **DF-042：流水线从失败检查点恢复**为例。需求不是「加个重试按钮」，而是「操作员可以恢复指定失败运行，不重跑已经提交的步骤，也不产生重复可见产物」。

{{< mermaid >}}
flowchart LR
    A["工单 / 用户反馈"] --> B["规格：目标与验收"]
    B --> C["调研与设计"]
    C --> D["实施计划与代码 PR"]
    D --> E["Review 与验证证据"]
    E -->|发现缺口| B
    E -->|满足交付条件| F["发布确认 / 回写领域文档"]
    F -->|运行反馈| A
{{< /mermaid >}}

{{< codex-table label="全流程产物与 AI 参与方式" >}}
| 阶段 | 产物 | AI 写什么、怎么校验 |
| :--- | :--- | :--- |
| 需求 | 工单 → `spec.md` | 整理目标、非目标与带 ID 的验收条件。例：`AC-01` 只重跑失败及后续待执行步骤；`AC-02` 重复请求不产生第二份可见产物；`AC-03` 恢复沿用原输入快照。未知行为写成待决问题，不擅自定为已确认 |
| 调研 | `research.md` | 比较原地继续、创建恢复运行、整条重跑；注明查了哪个版本，哪些结论来自资料、哪些来自实验。列出什么证据会推翻推荐，而不是罗列工具名 |
| 方案 | `design.md`，必要时链接 RFC 或 ADR | 定义恢复 API、运行状态、产物提交边界、兼容及回滚方案。明确例外：原快照不可读时应拒绝恢复，而非切换到最新数据 |
| 开发 | `plan.md` → 各任务分支与 PR | 拆出契约、后端、前端、集成验证，标出依赖。先共享双方使用的契约版本，前端可用 mock 并行，但最终要与真实后端联调 |
| Review | PR 讨论与 CI → `verification.md` | 用另一会话按规格和 diff 独立复核失败路径。比如恢复请求重发时，仅查 HTTP 返回码不能证明没有重复产物，还要核对持久化记录与产物索引 |
| 发布与回流 | 发布记录、运行观测 → `domains/pipelines/`、`runbooks/` | 更新交付的行为，记录发布版本和已验证环境；把确认的问题变成新工单或回归用例。合并不等于上线，灰度中的行为注明启用条件 |
{{< /codex-table >}}

`index.md` 是变更包的交接页：链接工单与各产物，只留当前阻塞、下一步和必要的基线指针。`verification.md` 只保留**验收 ID → 检查或证据链接 → 已测版本与环境 → 结论**。例如验证 `AC-02` 时，留下 CI 运行链接、被验证的提交、测试数据版本、产物计数及未覆盖场景；PR 有新提交后，判断受影响的证据是否需要重跑，不把旧结果标成新版本已通过。

图里的箭头不是瀑布流程。开发中发现原假设不成立，可以回改规格、通知已依赖它的任务并重查受影响的验收项。小修只用工单、PR 和回归记录；一般功能先合写一份变更说明，需要独立评审或反复引用时才拆文件。跨模块、破坏兼容或数据迁移的变更，再补齐相关章节。

## 4 AI 的规范放哪里，不全塞进 AGENTS.md

根 `AGENTS.md` 是每个新会话的路标，不是完整团队手册。[AGENTS.md 开放格式](https://agents.md/)给编码 Agent 一个可预测的入口；长文按任务显式链接，不假定各种工具都能自动加载 `docs/` 或采用相同的作用域规则。

```text
docs/engineering/ai/
├── index.md           # 任务类型 → 所需规则、模板和验证入口
├── context.md         # 如何读取生效规格、查证来源、标记未知
├── collaboration.md   # 多人/多 Agent 分工、worktree、交接与冲突
├── review.md          # 独立复核、验收证据、待验证项的写法
└── templates/         # 变更说明、交接、Review 结论的短模板
```

- **常驻约定写进 `AGENTS.md`。** 比如从 `docs/index.md` 找入口，按需求 ID 打开变更包，在哪里找正确的构建和测试命令，改变对外行为时更新对应领域说明。子目录确有不同约束再写局部入口。
- **按需规则写进 `docs/engineering/ai/`。** 比如调研如何标版本和证据，多个 Agent 各写哪些文件，怎样独立 Review，以及哪些结果必须标记为「未运行」「未覆盖」或「待确认」。这是团队认可的协作规范，不是提示词合集。
- **可执行的检查交给工程工具。** 可复用操作才封装为 Skill 或脚本；链接、元数据、接口兼容和所有者审查用 CI、测试和仓库规则执行。Markdown 不会授予部署权限，外部网页、调研材料和 PR 评论也不能当作新指令。

一条规则只维护一处。比如「何时需要验收证据」归测试或 Review 规范，`AGENTS.md` 只链接到它；如果 CI 才能强制阻止合并，就别把模板上的勾选框当作已经执行的门禁。

## 5 换人、换会话后，怎样不从头解释

接手人只需要一个需求 ID。工单里有变更包入口，变更包上能找到规格和当前 PR；**交接要共享可访问的版本，而不仅是路径。** 如果方案只存在某人的聊天或未提交的 worktree，另一位同事即使知道文件名也看不到。未合入的内容可通过团队能访问的 Draft PR 交接，但要标明尚未成为团队基线。

<details>
<summary>展开：DF-042 的交接记录示例</summary>

```text
需求：DF-042，失败流水线恢复；工单有变更包入口。
规格：spec.md @ <已确认规格所在提交>；本次 Review AC-01～03。
实现：后端 PR #218 @ <被验证的 HEAD>；前端 PR #223 依赖该契约。
决定：沿用原输入快照；不要切到最新数据集。
已验证：AC-01，CI #765，集成环境，固定输入快照 v17。
未验证：AC-02 的并发重发、AC-03 的原快照失效。
下一步：先跑这两个场景，再决定是否解除前端联调阻塞。
边界：不改调度器，不把尚未通过的检查写成已通过。
```

上面的编号和运行都是示意，实际交接用可点击的工单、PR、提交和 CI 链接。新同事可以直接对自己的 AI 说：「接手 DF-042。读取确认的规格和当前 PR，先指出基线、已验证和尚未验证的项，再执行下一步，不使用旧会话作依据。」

</details>

多人并行时，我会给每项变更指定一位集成负责人，各任务用独立分支或 worktree，避免两个 Agent 同时重写同一份规格。要改变验收条件，先在工单讨论并更新有效的规格版本，再让相关任务同步；发现冲突，先报告两个版本与影响，不靠 AI 私自选「看起来更新」的一份覆盖另一份。共享的是工程记录，不是彼此的聊天或私有工作区。

## 6 文档全由 AI 写，团队怎么防止失真

先给每类问题指定一个权威来源，再加自动检查：

- **「谁负责、现在排到哪？」** 看工单。变更包只记影响接手的阻塞和下一步，不维护第二套任务状态。
- **「约定应怎样？」** 看当前有效的领域规格；没交付的新行为看已确认的变更规格。机器接口以维护真实契约的 schema、迁移或接口定义为准，文档解释语义，不手抄字段表。
- **「实际跑成怎样？」** 看固定提交对应的验证证据，以及目标环境的发布和运行记录。规格、代码和运行结果不一致时，把差异作为问题报告，不让 AI 默默改文档去贴合代码。
- **「为什么这么设计？」** 看仍生效的 ADR 或变更设计，不从聊天记录或旧 PR 评论拼一个最终答案。

第一批检查只做能机械判定的事：链接有效、变更 ID 可定位、测试报告能对应被测提交。PR 模板补一个问题：**这次是否改变契约、领域行为或运维操作？若改变，哪些正式文档随之更新？** 对关键契约、运行手册和 AI 规范，按路径指定维护人；在 GitHub 上，`CODEOWNERS` 可以请求其 Review，若要强制审核，还需配置对应的仓库规则。[GitHub 的 CODEOWNERS 文档](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners)

落地不必大迁移。挑一个跨前端与后端的真实需求，只建 `docs/index.md`、一个变更包和一页 AI 协作规则；结束时让**不看原聊天**的同事带新会话接手一次。看他能否识别生效规格、找到失败或缺失的检查、在正确版本上跑出结果，以及过程中追问了几次。哪一处需要重新解释，再补哪一处的项目知识。

## 7 SDD 是什么，工具怎么选 {#sdd-tool-selection}

**SDD（Spec-Driven Development，规格驱动开发）是一种工作方式，不是一个编码工具。** 它把团队确认过的规格作为实现与验证的依据：先明确要改变的可观察行为、什么不改、怎样验收，再由 AI 规划、实现和验证。发现规格不成立就讨论并修订，不要求一开始把所有细节写死。流程可以完全用 Markdown、Git、工单和现有编码 Agent 实现。

拿 DF-042 来说，「加一个恢复按钮」只是任务；「两个并发恢复请求最多产生一份可见产物」才是可验证的规格。设计文档解释为什么采用某种恢复策略；回归测试证明被测实现是否满足这个场景。**写了长计划不等于做了 SDD：规格要能指导另一位同事实现，也要能指导 Review 判断结果。**

现阶段更准确的说法是：SDD 是 AI 开发中已有多种代表工具的做法，不是唯一主流，也没有可靠的全行业数据证明多数团队都在用。2026 年一项[开源 PR 实证研究](https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.ESEM.2026.84)没有发现样本里的规格相关记录能减少缺陷；作者同时说明，这些记录绝大多数是工单引用，样本没有提交 SDD 工具生成的产物，因此不能用这项研究判断具体工具的效果。

### 四个代表选项，不是四个同类产品

Codex、Claude Code、Cursor 等是可以承担读仓库、改代码、跑检查的**执行工具**；Spec Kit、OpenSpec 和 BMad 给执行过程提供不同结构；Kiro 则把规格工作流和执行工具集成在同一个产品里。团队可以统一规格格式，不一定要统一每个人用的 Agent。

{{< codex-table label="四种代表性 SDD 方案的场景对照" >}}
| 选项 | 最适合的场景 | 取舍 |
| :--- | :--- | :--- |
| [OpenSpec](https://openspec.dev/docs/quickstart) | 已有平台持续迭代：多个变更并行，新行为要能增量更新现有规格 | 最值得本平台先试；要明确归档和更新长期规格的责任，不能保留两份真源 |
| [GitHub Spec Kit](https://github.github.com/spec-kit/) | 团队想让不同 Agent 遵循一套可定制的规格、计划、任务与收敛流程 | 阶段和模板更明确；如果你们已有成熟工单和模板，先确定它替代什么，避免重复填报 |
| [Kiro Specs](https://kiro.dev/docs/specs/) | 团队愿意采用同一开发环境，希望在一个界面里评审需求、设计、任务并执行；也有独立缺陷流程 | 默认工作流省集成，但要先试团队环境、权限和产物的可移植性；不因为用了 Specs 就必须全员换工具 |
| [BMad Method](https://docs.bmad-method.org/start/how-bmad-works/) | 需求还不清楚，必须先厘清产品目标、架构与交付拆分，再进入开发 | 产品和架构角色更突出；已有明确边界的日常改动不必套完整流程 |

**我的选择：不换现有 Agent，先用一项跨前后端的数据飞轮需求试行轻量 SDD。** 只要求可验收规格、必要的设计、对应 PR 和证据。文案修正和影响明确的小缺陷继续用工单加回归；跨模块功能走变更包；数据迁移、版本契约和权限边界改动，再补兼容、回滚和针对性审查。

如果试点发现，最费时间的是把已完成的变更合回当前规格，优先试 **OpenSpec**，让 `openspec/changes/` 取代 `docs/changes/` 的同类职责。若真正痛点是每个 Agent 都以不同顺序产出材料，优先试 **Spec Kit**。比较工具时，用同样的需求类型记录**换人接手耗时、重复确认次数、验收漏项和返工**，而不是比谁生成的文件多。

数据飞轮要保留数据从哪来、怎么变、最后验证成什么样。开发文档同样要讲清楚：**决定从哪里来，进了哪次变更，由什么证据验证。** 这条链可查，AI 写得再多，团队也不必从头对齐。
