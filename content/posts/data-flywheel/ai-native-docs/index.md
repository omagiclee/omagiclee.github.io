假设质检员把一批模糊图片标记为「剔除」。质检页面上，这些图片消失了；下一轮训练却仍然读到了它们。负责质检的 AI 验证了列表不再显示这些图片，负责训练的 AI 则确认任务仍然读取指定的数据集版本。两个检查都通过了，但没有一个检查回答用户真正关心的问题：**被剔除的图片还会不会进入下一轮训练？**

问题出在「剔除」没有一条共同确认的定义：它只是把图片从质检列表隐藏，还是要生成一个不含这些图片、供下一轮训练使用的新数据集版本？如果答案只留在某个会话里，换一个人或换一个 AI，仍然得重新问。

我会把项目文档分成三类：**这次改什么，平台现在怎么工作，团队平时怎么协作。** 第一类跟着需求走，第二类长期维护，第三类告诉新人和 AI 从哪入手。下面先讲目录，再用一项流水线恢复需求走一遍从规格到验收的过程。

## 先按读者要找的东西分目录

接一个需求的人想知道「现在做到哪了」，维护模块的人想知道「当前规则是什么」。如果把需求、调研、方案和审查分别塞进四个全局目录，接手人就得去四处拼故事。更自然的做法是：**把同一次变更放在一起，再为跨版本仍有用的知识留一个固定位置。**

```text
repo/
├── README.md                         # 项目是什么，怎么启动
├── AGENTS.md                         # 给编码 Agent 的短入口
└── docs/
    ├── index.md                      # 文档地图：按需求、领域或任务找
    ├── changes/
    │   └── DF-042-pipeline-resume/
    │       ├── index.md              # 一页摘要、链接和接手点
    │       ├── spec.md               # 要改什么、不改什么、怎样验收
    │       ├── research.md           # 查过哪些方案，证据支持什么
    │       ├── design.md             # 选了什么方案，为什么
    │       ├── plan.md               # 怎么拆任务，哪些要先做
    │       └── verification.md       # 什么版本、跑了什么、结果如何
    ├── domains/                      # 数据集、流水线、算子、筛选与评测
    ├── architecture/                 # 系统边界、架构图、重要决定
    ├── guides/                       # 比如怎样注册一个新算子
    ├── runbooks/                     # 比如怎样定位失败、恢复和回滚
    └── engineering/
        ├── testing.md                # 测试与发布验证规则
        └── ai/                       # AI 协作手册与交接模板
```

**变更包**就是 `changes/` 下某个需求的一组文件。上面展示的是复杂变更的完整形态，普通功能可以只用一页。工单继续管负责人、优先级和进度；代码审查的讨论留在 PR；变更包用链接串起这些记录，不另外维护一套进度表。如果一个需求跨多个仓库，选一处存放变更包，各仓的 PR 都回链同一需求编号。

**长期文档**回答的是「现在怎样」。例如，流水线领域文档说明一次运行有哪些状态、什么时候可以恢复；接口字段以仓库里的接口定义为准，不在 Markdown 里再抄一遍。架构文档说明调度、执行和产物存储怎样分工。只有日后仍会被问「当初为什么这么选」的决定，才值得单独写一条架构决策记录（ADR）。若方案会影响多个团队，可以先用提案（RFC）征求意见；提案和最终决定需要区分。

这些做法可以组合，不必选边站。[Docs as Code](https://backstage.io/docs/features/techdocs/) 解决的是怎样用 Git 和 PR 管文档版本；[Diátaxis](https://diataxis.fr/) 解决的是怎样区分教程、操作指南、参考和原理说明；[RFC](https://rust-lang.github.io/rfcs/) 和 [ADR](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions) 分别用于讨论提案和保留决定。它们都不要求把同一需求拆到不同地方。

## 走一遍：从「加按钮」到「确认没有重复产物」

### 先写出什么才算做对

「提供恢复按钮」是一项功能描述，不能用它来判断恢复做得对不对。这个示例里，我会让 AI 先把用户反馈整理成三个可检查的条件，请需求负责人确认：

- **AC-01：**从失败的步骤继续，不重跑已经完成的步骤。
- **AC-02：**即使两个请求同时尝试恢复同一次运行，也最多产生一份可见的产物。
- **AC-03：**恢复时使用原来的数据集快照；原快照不可读就报错，不能悄悄改用最新数据。

写成这样，前端知道应该显示哪些状态，后端知道哪些行为不能破坏，审查者也知道要查什么。文档可以全部由 AI 起草和更新，但「提出一个规则」和「团队确认这个规则」不是同一件事。后面如果发现条件不合理，可以改，但要更新规格并通知依赖它的任务，不能只在某个会话里改口。

### 调研、设计和开发围着这个问题转

调研先查当前系统能从哪里拿到已完成的步骤和产物记录，再比较原地继续、创建恢复运行和整条重跑。记录查过的代码版本、实验的实际结果和还没验证的假设。整条重跑可能最容易实现，但如果会再次写入之前的产物，就不符合这次验收要求。

设计负责回答「从哪个步骤继续、怎样识别重复请求、显示什么错误」，实施计划负责回答「依赖谁先做什么」。例如，前后端先共用一版接口契约，前端可以先用模拟数据开发，最后再与真实后端联调。不同会话可以并行写代码，但不应该各自决定请求和响应是什么样。

### Review 回到规格，发布后再更新长期说明

让另一个 AI 会话直接读规格、改动和测试，不以实现者的总结为结论。拿 AC-02 来说，两个请求返回成功，不代表没有重复产物。检查要看实际写出的产物索引，并在验证记录里注明被测提交、测试环境和运行链接。没有测过并发重发，就写「未验证」；旧提交跑过，也不能直接当成新提交的结果。

代码合并后，变更包仍保留当时怎么做、测了什么。等功能真正上线，再确认流水线领域说明和运维手册反映了目标环境的行为；还在灰度就注明启用条件。**变更包记这次发生了什么，长期文档告诉下一位读者现在可以依赖什么。**

## AI 规则怎么放，换人时怎么接

`AGENTS.md` 不必解释整个项目。它只放新会话每次都该知道的内容：从哪里找文档，按什么方式找到本次需求，用哪些入口构建和测试。AI 专用但不需要每次重读的规则，放进 `docs/engineering/ai/`，例如：

- **调研：**区分已从源码确认的行为、实验结果和待核实的猜测。
- **协作：**按需求或任务分支工作；共享接口变了，要通知依赖它的人，而不只是改自己的文档。
- **审查：**按验收条件复核，注明哪些没有运行、没有覆盖或仍待确认。

把这些规则按任务链接起来就够了。能用 CI 检查的事，例如链接是否失效、回归是否通过，交给 CI；不要让团队靠记住一长串提示词来维持一致性。[AGENTS.md](https://agents.md/) 提供的是约定俗成的入口，[OpenAI 的工程案例](https://openai.com/index/harness-engineering/) 则展示了短入口、版本化知识和自动检查如何配合。

真正交接时不必粘贴整段聊天。下面这种记录放在变更包首页，读起来更接近一条同事留言：

> **DF-042 · 流水线失败后恢复**
>
> - **从哪开始：**读已确认的规格版本，再看后端 PR 和被测提交。
> - **已经验证：**失败后可从正确步骤继续；集成测试记录见 PR。
> - **还没验证：**并发恢复会不会重复写产物，原快照不可读时能否正确报错。
> - **下一步：**先补这两个检查，再继续前后端联调。

正式使用时，给规格、PR、被测提交和测试运行加上链接。未合入的资料可以放在团队有权访问的草稿 PR 里，并注明尚不是正式版本。接手同事开一个新会话，只需要说：「接手 DF-042，从工单链接的交接页开始。」能不能继续，取决于资料和版本是否共享，而不是两个会话有没有同一份记忆。

## SDD 是什么，工具怎么选？ {#sdd-tool-selection}

前面那三个验收条件，就是**规格驱动开发（Spec-Driven Development，SDD）**的起点：让明确的规格指导实现和验证，而不是等代码写完，再从代码反推需求。它不是一款编码工具。Codex、Claude Code 或 Cursor 可以执行工作；SDD 约定的是执行依据与验收方式。只用 Markdown 和 Git 也能做，不必先换工具。

SDD 是有多种工具支持的开发方式，但没有足够的行业数据把它说成多数团队的标准。[一项 2026 年开源 PR 研究](https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.ESEM.2026.84) 没发现样本中的规格相关记录能降低缺陷；样本主要是工单引用，并未直接评估这些 SDD 工具。对团队更实用的判断是：它能不能减少交接时的误解，并让验收更容易做对。

{{< codex-table label="SDD 工具与适用场景" >}}
| 选项 | 什么时候值得用 |
| :--- | :--- |
| [OpenSpec](https://openspec.dev/docs/quickstart) | 已有系统改动多，常搞不清正在做的变更和当前有效的规格。它把两者分开，归档变更时再更新规格。 |
| [GitHub Spec Kit](https://github.github.io/spec-kit/) | 大家使用不同 Agent，想共用从规格、计划、任务到实现和检查的流程，而不是各写各的。 |
| [Kiro Specs](https://kiro.dev/docs/specs/) | 团队愿意使用集成开发环境，希望在同一个界面写需求、审方案、拆任务和执行。 |
| [BMad Method](https://docs.bmad-method.org/start/how-bmad-works/) | 需求还不明朗，需要先做产品判断、架构设计和交付拆分。问题已经清楚的小改动，不必走完整流程。 |
{{< /codex-table >}}

**对已有的数据飞轮平台，我会先用现有 Agent 和一页变更说明做试点。** 挑一个涉及前后端的需求，让没参加原讨论的同事在新会话里接手。看他用了多久找到正确的规格，是否知道哪些检查没跑，以及需要回来问什么。如果困难在于「改完了，但长期规格总没更新」，再试 OpenSpec；如果困难在于「每个 Agent 都按不同流程交付」，再试 Spec Kit。普通小修继续用工单、PR 和回归测试就够了。

这套文档最终是给人读的。检验它的办法也很简单：**作者不在场时，下一位同事能不能从一条链接找到该信的版本，并动手完成下一步。**
