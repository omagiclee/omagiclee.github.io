一段白天视频，可以生成雨天、夜间和逆光版本；一张干净的产品图，可以生成划痕、污渍和破损样本。生成模型让数据扩充更容易，也把一个问题推到了训练之前：**这些变化是否符合任务要求，标签是否仍然成立，模型能否从中学到对真实数据有用的东西？**

NVIDIA 在 **2026 年 10 月 21 日**更新了 Cosmos Data Factory，列出驾驶数据集、图像属性、事件视频、缺陷图像和视频条件扩充五类蓝图。它把整理、标注、生成与评估组织成可组合的工作流。[官方更新](https://blogs.nvidia.com/blog/cosmos-open-train-evaluate-deploy-world-models/)

对影像画质 AutoGT，最值得借鉴的是这套生产与筛选闭环。**生成结果先作为候选，经过任务检查、独立审核和真实域实验，再决定如何进入训练。** 其中，“生成得自然”和“可以作为像素真值”需要分别判断。

本文承接[影像画质 Auto GT 生成方案与数据平台设计]({{< relref "/posts/data-flywheel/image-quality-auto-gt/index.md" >}})。官方能力按 **2026 年 10 月 23 日**可见文档理解；AutoGT 接入和实验部分为工程设计。

## 1 五类蓝图分别生产什么

Cosmos Data Factory，简称 **CDF**，由参考蓝图、可组合组件和 Agent skills 构成。Agent 负责组织和调用流程，生成、标注与检查仍由具体模型和程序执行。[CDF 官方仓库](https://github.com/NVIDIA/cosmos-data-factory/blob/c2ad83822e25b5ceef1a67d848bbc728c5355134/README.md)

{{< codex-table label="Cosmos Data Factory 五类参考蓝图" >}}
| 蓝图 | 主要变化 | 对数据生产的价值 |
| --- | --- | --- |
| 驾驶数据集生成 | 检索驾驶场景并补充变体 | 扩充特定场景覆盖 |
| 图像属性扩充 | 改服装、颜色、鞋履等外观 | 增加检索与重识别训练样本 |
| 事件视频生成 | 从种子图生成异常事件视频 | 补充难采集事件 |
| 缺陷图像生成 | 在产品图中生成缺陷 | 补充工业检测正样本 |
| 视频数据扩充 | 改天气、光照和环境条件 | 在场景保持约束下增加条件变化 |
{{< /codex-table >}}

表中具体用途来自 [CDF 蓝图说明](https://github.com/NVIDIA/cosmos-data-factory/blob/c2ad83822e25b5ceef1a67d848bbc728c5355134/README.md)。对影像任务，最后两类最值得拆解，但需要注意两个词义：

- **Video Data Augmentation** 在这里主要指训练数据扩充；不能直接理解为去噪、超分或画质修复。
- **Defect** 主要指 PCB、金属、玻璃等产品缺陷；噪声、振铃、涂抹、色偏属于成像或处理缺陷，需要另建任务定义。

例如，把晴天变成雨天，对目标检测可能仍是同类场景扩充；对画质恢复，却不自然形成“雨天输入—晴天真值”。天气、反射、遮挡和可见内容都可能变化。

### 影像画质需要选择合适的监督形式

{{< codex-table label="生成方式与可用监督形式" >}}
| 生产方式 | 数据关系 | 优先用途 | 接收前要确认什么 |
| --- | --- | --- | --- |
| 可靠参考图经过受控退化 | 已知参考与合成输入 | 去噪、压缩恢复、超分等配对训练 | 退化是否接近真实相机域 |
| 固定场景的物理重渲染 | 已知条件下的配对 | 重打光、景深等条件监督 | 几何、颜色与采样是否一致 |
| 生成式修改光照或天气 | 原图与生成候选 | 鲁棒性训练、受限伪监督、偏好学习 | 内容保持、变化范围与标签有效性 |
| 生成式插入局部缺陷 | 干净图、缺陷图与条件掩码 | 检测、分割、异常识别 | 缺陷是否实际出现且匹配掩码 |
{{< /codex-table >}}

这是任务选择框架。对已有可靠参考的恢复任务，可以先采用“保留参考、合成退化”的路线。Real-ESRGAN 通过高阶退化建模构造训练对，说明合成数据的价值也可以来自对退化过程的建模。[Real-ESRGAN 原论文](https://arxiv.org/abs/2107.10833v2)

## 2 从生成器到数据工厂

CDF 的核心组件涵盖检索整理、仿真、生成扩充、异常生成、自动标注和编排。当前参考蓝图通过 CDF Orchestration 运行 Airflow DAG；支持 Kubernetes，事件视频与视频扩充也提供 OSMO 后端。接入已有数据飞轮时，可以复用单个组件，不必先迁移整个平台。[CDF 架构与组件](https://github.com/NVIDIA/cosmos-data-factory/blob/c2ad83822e25b5ceef1a67d848bbc728c5355134/README.md)

下面是一条适合接入 AutoGT 的闭环。图中的正式发布和训练反馈由数据平台负责。

{{< mermaid >}}
flowchart TD
  A[真实失败样本与覆盖缺口] --> B[选择源数据并隔离来源组]
  B --> C[冻结生成配方与允许变化]
  C --> D[生成候选]
  D --> E[自动检查与任务审核]
  E -->|通过| F[标注复核与数据集版本]
  E -->|拒绝或不确定| G[记录原因和局部证据]
  G --> C
  F --> H[训练并在独立真实集评测]
  H --> A
{{< /mermaid >}}

`cdf-augmentation` 已经支持把生成与可选评估串起来：候选质量失败时，可以增加 seed 后重试；外部服务失败则停止，避免把服务错误当作需要再生成一次的质量问题。模型通过 HTTP endpoint 接入，生成组件本身不携带模型权重。[Augmentation 官方说明](https://github.com/NVIDIA/cdf-augmentation/blob/main/README.md)

但“流程成功”“检查通过”“可作为训练监督”仍是不同状态。官方 VDA 输出说明也区分原视频和生成视频的标注、导出分支，**没有提供合并后的最终数据集 manifest**。进入现有平台时，仍需要统一来源、审核和数据集版本。[VDA 产物契约](https://github.com/NVIDIA/cdf-orchestration/blob/main/skills/cdf-video-data-augmentation/references/outputs.md)

## 3 官方评估器能筛掉哪些问题

### 视频检查需要按实际测量对象理解

Cosmos Evaluator 当前 README 列出四种检查，既可作为 REST 服务，也可通过 Python 使用。它们提供不同维度的证据，不能相互替代。[Evaluator 官方说明](https://github.com/NVIDIA/cosmos-evaluator/blob/main/README.md)

{{< codex-table label="Cosmos Evaluator 的检查对象和适用边界" >}}
| 检查 | 实际看什么 | 结果怎样使用 |
| --- | --- | --- |
| Hallucination | 生成视频的运动区域是否偏离原视频运动区域 | 检查新增异常运动，另查静态细节和内容丢失 |
| Objects | 生成对象是否对应预期真值位置 | 依赖可用的对象与几何参考，不能套用于任意视频 |
| Attribute Verification | 语言与视觉模型判断目标属性是否成立 | 用于天气、光照等语义核验，保留回答与不确定性 |
| Physical Plausibility | 视频表征与分类器判断运动是否合理 | 用作可校准的质量信号，另查具体物理约束 |
{{< /codex-table >}}

表中“怎样使用”是接入建议。两个实现细节尤其影响筛选设计：

**运动检查存在方向性。** 专门文档说明，它惩罚远离原动态区域的新增动态像素，不识别只存在于原视频的运动；长度不同时，只对共同部分打分并忽略未匹配尾部。因此，物体被删掉、静态文字被改掉、尾部异常，都需要额外检查。[Hallucination 检查细节](https://github.com/NVIDIA/cosmos-evaluator/blob/main/docs/checks/hallucination.md)

**物理合理性分数来自训练标签。** 当前实现使用冻结的视频编码器和分类器，默认分类器学习的是 FineVideo 质量标签；文档明确说明，它不测量具体物理量，也不保证满足物理定律。当前抽取 64 帧，帧间短暂异常仍可能漏检。[Physical Plausibility 检查细节](https://github.com/NVIDIA/cosmos-evaluator/blob/main/docs/checks/physical_plausibility.md)

这也解释了为什么不能统一配置一个“质量分大于 0.8 就入库”。每个检查的含义、适用输入和阈值都不同。对于刻意加入雨雪的任务，还需要用样例确认运动检查是否把预期天气变化误判成异常。

### 缺陷生成同时检查真实感和掩码有效性

AnomalyGen 接收干净产品图和目标掩码，通过适配后的生成模型制造缺陷，再进行评估、可选重生成、筛选和伪标注。[AnomalyGen 官方流程](https://github.com/NVIDIA/cdf-anomalygen/blob/main/README.md)

它的评估教程把质量拆成两组：一组用 DINOv2 特征的最近邻对应度观察合成缺陷与真实参考的相似性；另一组用 completeness、precision、boundary IoU 等代理检查缺陷是否填充指定区域、变化是否外溢、边界是否对应。筛选可以按缺陷类别分别排序，避免只保留容易生成的类别。[AnomalyGen 评估与筛选](https://github.com/NVIDIA/cdf-anomalygen/blob/main/docs/tutorial/texture/6-evaluation-and-refinement.md)

这套思路适合迁移到画质 AutoGT：**既看目标区域有没有达到要求，也看其他区域有没有被意外修改。** 但条件掩码只是生成意图，最终图像中的有效标签还要复核；图像与真实缺陷相似，也不能单独证明标签正确或训练有效。

## 4 面向 AutoGT 的五层筛选设计

对一张低照人像，先规定任务：改善面部可见性，保持身份、表情、衣服纹理和文字，允许光照与色调在目标范围内变化。随后按成本从低到高检查，让失败原因能够定位到具体环节。

{{< codex-table label="AutoGT 生成候选的五层筛选" >}}
| 层次 | 要回答的问题 | 检查例子 | 处置 |
| --- | --- | --- | --- |
| 1 文件与配对 | 输入和产物能否正确使用 | 解码、摘要、尺寸、帧数、时间戳、颜色空间、配对关系 | 缺失或错误先隔离 |
| 2 任务条件 | 要求的改变是否发生 | 光照目标、缺陷类别、退化强度、编辑区域 | 未完成就拒绝或重生成 |
| 3 内容与标签 | 不该变的是否保留 | 人脸局部、文字、结构、掩码边界、轨迹和遮挡 | 漂移则拒绝或改用其他监督 |
| 4 局部与时序质量 | 有没有新伪影 | 发丝光晕、皮肤涂抹、纹理闪烁、色彩跳变 | 结合局部检查与人审 |
| 5 覆盖与数据价值 | 是否补足了训练缺口 | 相机域、场景、困难程度、近重复和来源组 | 分层采样后进入训练实验 |
{{< /codex-table >}}

### 质量门不能把任务本身筛掉

去噪训练的输入应当有噪声，背景虚化的目标应当包含失焦区域，低照扩充本来就可能更暗。如果用同一个“清晰、明亮、少噪声”规则检查所有角色，会删除最需要的样本。

检查器至少要知道 **任务、输入或目标角色、允许变化区域、参考类型**。PSNR、SSIM 等参考指标需要可靠对齐、明确目标和一致计算域；“重打光输出与原图更相似”不等于完成了重打光。无参考画质分适合辅助排序，也不能证明眼睛、文字或皮肤纹理忠实。

感知自然度与参考失真本身就可能产生权衡。《The Perception-Distortion Tradeoff》对此给出了理论分析；落到数据筛选，应分别报告自然度、保真和任务完成情况。[原论文](https://arxiv.org/abs/1711.06077v4)

### 硬约束先判断 分数用于同类候选排序

如果任务明确要求保留身份，身份漂移就是拒绝理由，不能用更好的曝光分抵消。通过硬约束后，再在同一任务、同一场景层内比较候选；自动检查无法确定的样本进入复核队列。

未执行、不适用、超时和无法判断应单列状态，不能计为通过。导入时核对实际执行过哪些检查及其版本，避免把关闭检查后的流程成功误当成质量验收。

审核界面可以只保留原图、候选、局部放大、接受或拒绝，以及极短原因。可复用原因包括：身份漂移、文字改变、边缘光晕、掩码错位、时序闪烁、目标未达成。拒绝样本保留为诊断数据，供下一轮修改配方。

<details>
<summary>展开阈值校准与人审抽样方法</summary>

先建立小规模、分层且独立于最终测试集的审核集，覆盖正常、困难和明确失败的候选。审核者按同一任务规范标记可接受性，分歧样本单独仲裁，再选择阈值。

记录两个容易混淆的数：

- **放行集合中的坏样本占比**：人工判坏且自动通过的数量，除以人工抽检的自动通过数量。
- **坏样本漏检率**：人工判坏且自动通过的数量，除以全部人工判坏数量。

前者描述接收集合的污染，后者描述检查器识别坏样本的能力。还要统计好样本误拒率，并分别看低照、肤色、设备和运动等子组。

量产抽检同时覆盖随机通过样本、阈值附近样本、检查器互相矛盾的样本和部分拒绝样本。估计总体污染时按抽样概率加权，不能把刻意多抽的困难样本直接当总体比例。置信区间按独立来源组估计，同一视频的多帧或同图变体不能充当独立样本。

生成模型、检查器或数据域变化后重校准。用同一个评分器反复挑选最佳候选，再拿它证明质量提升，容易只优化到该评分器的偏好；应另用独立人工集和真实下游任务验证。

</details>

## 5 接入已有 AutoGT 与数据飞轮

现有[影像 AutoGT 方案]({{< relref "/posts/data-flywheel/image-quality-auto-gt/index.md" >}})已经将参考来源与审核状态分开，包含本地退化、二维近似虚化和已有配对导入。CDF 可以作为新的外部候选生产器，沿用配对审核、失败回流和版本发布的思路。

生成式重打光输出即使被人工接受，仍保留 `generated_pseudo` 属性；对它进一步施加可重放退化，也不会把源图变成实拍观测。参考来源、配对构造方式和审核结果需要分别保存。

{{< mermaid >}}
flowchart TD
  A[CDF 候选与运行记录] --> B[导入适配器核对文件和来源]
  B --> C[自动检查与配对审核]
  C -->|拒绝| D[原因与 ROI 进入诊断集]
  C -->|接受| E[候选数据集]
  E --> F[标注与独立审核]
  F --> G[来源隔离检查与正式发布]
  G --> H[训练实验与真实域报告]
  D --> I[新版本配方]
  I --> A
{{< /mermaid >}}

这张图是接入设计，尚未代表现有平台已经运行 CDF。第一步适合做单帧或明确抽帧配对导入；连续视频还需要扩展 clip、时间戳、轨迹与时序审核契约，不能把一组图片接口直接当成完整视频数据集接口。

{{< codex-table label="CDF 接入 AutoGT 的职责分配" >}}
| 环节 | 主要职责 | 保存的证据 |
| --- | --- | --- |
| CDF 或其他生成器 | 执行生成、模型检查、有限重试 | 模型版本、配方、seed、输入输出、检查结果 |
| 导入适配器 | 校验真实产物并关联来源 | 文件摘要、父候选、源组、缺失项 |
| AutoGT 审核 | 判断配对与监督用途 | 参考类型、审核版本、拒绝原因、局部区域 |
| 数据集管理 | 复核标签、隔离来源并冻结版本 | 划分、标注、审核、manifest 与对象摘要 |
| 训练评测 | 验证真实域收益并回流失败 | 数据版本、实验配置、子组指标、失败案例 |
{{< /codex-table >}}

### 来源分组应先于数据扩充

同一原图的不同 seed、同一视频的相邻片段、同一人物或场景的近重复采集，应按评测目标建立来源关联。先将独立来源组划入训练、校准、验证与测试，再从训练池扩充。合成结果继承来源组，发布时再次检查。

文件摘要只能发现精确重复。人物身份、不同编码的视频和相似场景还需要显式来源信息或近重复检查。最终真实测试集不能用于挑 prompt、选择生成参考、调筛选阈值或进行候选最近邻检索，否则测试反馈已经参与了数据生产。

## 6 用训练对照实验验证筛选价值

筛选可能删除错误监督，也可能删掉困难但有效的长尾样本。因此，需要同时问两个问题：筛选后的模型是否更好，以及留下的数据是否仍覆盖目标问题。

建议首轮只选一个任务，例如低照人像重打光；固定源池与生成预算，对比以下实验。表中是**实验方案，不是已测结果**。

{{< codex-table label="合成数据与筛选策略的训练对照实验" >}}
| 组别 | 训练数据 | 要验证什么 |
| --- | --- | --- |
| A | 固定真实训练集 | 基线表现 |
| B | A 加常规任务适用增强 | 简单增强已经能带来多少收益 |
| C | A 加生成候选的分层随机子集 | 增加生成数据本身的效果 |
| D | A 加自动筛选后的同规模子集 | 筛选相对随机选择的价值 |
| E | A 加自动筛选与人工复核后的同规模子集 | 人审增加的收益和成本 |
{{< /codex-table >}}

C、D、E 使用同一候选池、相同新增样本数和相同场景配额；C 也必须通过解码、来源与格式等基础检查，只省略研究中的质量筛选。如果某一困难场景不足配额，就按各组共同可满足的规模比较，另外报告该场景的通过率。

评价在隔离的真实数据上进行。重打光优先看目标完成、身份与局部内容保持、盲评偏好；有可靠配准参考的恢复子集，再计算参考误差。视频增加时序稳定性；缺陷检测则看真实缺陷召回、定位和正常产品误报。

{{< codex-table label="合成数据实验需要同时报告的结果" >}}
| 维度 | 建议报告 | 为什么需要 |
| --- | --- | --- |
| 真实任务效果 | 主指标及多次训练的波动 | 区分稳定收益与偶然变化 |
| 困难子组 | 低照、逆光、运动、设备等子组效果 | 防止总体均值掩盖退化 |
| 内容保真 | 身份、文字、局部结构失败率 | 避免更自然却改错内容 |
| 训练覆盖 | 独立来源组数、子组数量、近重复率 | 防止大量变体虚增有效数据量 |
| 筛选代价 | 通过率、误拒、人工分钟、重试次数 | 判断投入是否值得扩大 |
{{< /codex-table >}}

<details>
<summary>展开避免实验混淆的控制项</summary>

固定模型初始化策略、训练步数、batch size、真实与合成采样比例、损失与验证协议；用多个随机种子报告均值与波动。不要让“增加数据”同时变成“多训练了一倍”，再把所有收益归给数据质量。

第一组实验固定生成预算与训练样本数，研究选择策略。第二组实验再固定总生产预算，允许各策略产量不同，研究实际成本下的收益。两种比较回答不同问题。

生成器和检查器的选择只使用训练与校准数据，混合比例等超参数在验证集选择。最终测试集冻结；通过测试发现的新失败可进入下一版开发数据，但需要另留新的独立测试集。

不要只优化接受率。低接受率可能表示质量差，也可能表示正在挑战有价值的困难场景；应同时观察该场景的真实任务收益和独立来源覆盖。

</details>

## 7 从小批次开始计算有效成本

对已有 AutoGT 平台，首轮可以按以下顺序推进。这里的规模是便于发现工程与筛选问题的试验起点，不是统计充分性的保证。

{{< codex-table label="合成数据工厂的最小验证顺序" >}}
| 阶段 | 建议起点 | 验收重点 |
| --- | --- | --- |
| 契约打通 | 10 个源样本，每个 2 个候选 | 文件可读、来源完整、检查结果与审核可追踪 |
| 筛选校准 | 约 200 个独立来源组，覆盖若干困难子组 | 误放、误拒、检查器分歧与人工规范 |
| 训练验证 | 根据任务与统计功效确定规模，执行 A 至 E 对照 | 真实域收益、保真和子组退化 |
| 扩大生产 | 对有收益的场景追加预算 | 收益、覆盖与成本持续可接受 |
{{< /codex-table >}}

部署也应按环节拆开。`cdf-augmentation` 的模型可以通过外部 HTTP 服务运行，但其官方容器的 H.264 本地解码和部分对齐处理仍有 GPU 依赖。完整 VDA 蓝图还包含标注、检查与并行任务，不能把“远程模型推理”理解为整条蓝图无需 GPU。[Augmentation 运行条件](https://github.com/NVIDIA/cdf-augmentation/blob/main/README.md)、[VDA 执行与容量说明](https://github.com/NVIDIA/cdf-orchestration/blob/main/skills/cdf-video-data-augmentation/SKILL.md)

本地工作站可以先承担审核、来源管理、轻量检查与实验报告；重生成和特定检查器放到符合其依赖的执行环境。这样先验证每个候选能否被解释和筛选，再决定是否部署完整集群。

成本按“最终可用数据”计算：

```text
每个接受样本的成本
  =（生成 + 检查 + 人审 + 存储传输 + 失败重试总成本）
    ÷ 最终接受且去重的样本数
```

还应单列独立来源组数量，以及每个新增有效场景的成本。同一张图生成一百个近似变体，可能增加审核和训练开销，却没有增加多少覆盖。

当某类样本持续出现身份漂移、标签错位或真实域负收益，优先修改条件、生成器或监督用途；保留失败证据并限制重试预算。扩大生产的依据，应是独立真实评测中的稳定收益，以及可以承受的数据成本。
