假设一位研究员点了「重新导出」，想取回上周训练用的那一批样本。下载成功，版本号没变，样本数也对。直到下一轮评测才发现：**拿到的不是原来那批数据。**

前端保留了旧版本号，后端却按最新规则重新筛选。团队用同一个词描述了两种行为，各自的 AI 实现和测试都说得通，合在一起却不对。

## 为什么代码、聊天和工单加起来还不够

代码记录**怎么做的**，聊天记录**怎么讨论的**，工单和 PR（合并请求）记录**谁在做、改了什么**。但接手人最想知道的是：**团队最后定了什么，我怎么知道它已经做对？**

AI 不会自动知道哪些聊天结论已经被采纳。只读代码，新会话可能把缺陷当成规则；只读聊天，它又可能把提议当成决定。文档不必复制这些记录，只需要补上两者之间缺失的连接：把**生效规格、实际改动和验证结果**连起来。

## 先把「重新导出」写成可验收的行为

{{< admonition type=info title="示例规格：重导历史版本不能换样本" >}}
使用原快照的样本清单；如果快照不可用，就明确提示，不用现行规则重新计算。
{{< /admonition >}}

这一句就能决定前端该显示什么、后端该返回什么，又不限制由哪个服务读取快照。它也让调研和审查有了具体目标：

- **调研**：旧版本有清单吗？如果部分历史快照早已过期，先决定兼容范围，不让 AI 自行补一个「能下载」的替代方案。
- **开发**：先约定快照不可用的响应，再并行实现。设计细节可以后定，需求含义不能各自解释。
- **审查**：修改筛选规则后重导历史版本，比对**样本 ID 清单**，不只对数量。记录被测提交和运行链接；没测快照过期，就明确写没测。

## 哪条信息放哪儿？

{{< codex-table label="按问题定位到对应的项目记录" compact="true" >}}
| 想知道什么 | 去哪里找 |
| :--- | :--- |
| 这次改什么？ | **变更包**：重导需求、兼容范围和相关 PR。 |
| 现在适用什么规则？ | **领域文档**：已交付的重导规则，下次改保留期可直接引用。 |
| 什么已经证实？ | **CI 和发布记录**：哪个提交测过清单一致，哪个环境已经上线。 |
| 新人和 AI 怎么接手？ | **协作手册**：从哪里找现行规格，怎样核验，如何记录未验证项。 |
{{< /codex-table >}}

工单继续管排期和责任，不把这些信息再抄进仓库。变更包只留关键取舍和链接；一次改动跨几个仓库，也只用一个需求编号。领域文档维护**今天的规则**，旧变更包保留**当时为什么这么决定**。

## 什么时候值得引入 SDD 工具？

[规格驱动开发（SDD）]({{< relref "/posts/data-flywheel/ai-native-docs/index.md#sdd-tool-selection" >}})在这里的用处，是让**同一份规格**既指导实现，也指导验证。先解决反复发生的问题，再选工具：

- **没有共同决定**：先试一页规格。换工具不会替团队决定「重新导出」的含义。
- **现行规则和提案经常混在一起**：试 [OpenSpec](https://openspec.dev/docs/quickstart)，把两者分开。
- **不同 Agent 总漏掉交付材料**：试 [Spec Kit](https://github.github.io/spec-kit/)，统一规格、计划和检查。

## 用一次真的交接验收

选一个跨前后端的需求，在做到一半时，交给一位没参加原讨论的同事。**只给需求编号，让对方用自己的 AI 开新会话。** 不要求他复述文档，要求他实际完成一步，例如补测一次快照过期。

{{< codex-table label="根据接手遇到的问题改进文档" compact="true" >}}
| 卡在哪里？ | 优先修什么？ |
| :--- | :--- |
| 不知道从哪读起 | 补工单到变更包的入口。 |
| 找到两份互相冲突的规定 | 标清哪个版本生效、谁负责更新。 |
| 看完仍不知道怎么算通过 | 把验收条件写成可观察的行为，并链接已有证据。 |
{{< /codex-table >}}

如果作者不在场，下一位同事还能找到正确的版本、说清哪些没验证，并动手完成下一步，这套文档才值得继续维护。
