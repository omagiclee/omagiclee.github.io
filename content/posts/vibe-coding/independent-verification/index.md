AI 写完实现，又补齐测试，最后交付一句“全部通过”，很容易让人觉得任务已经完成。但实现与测试可能来自同一个理解：**如果它误读了需求，测试也可能把这个误读当作正确答案。**

因此，验证需要尽量对照原始需求和可信样例；对于重要改动，再增加一个独立上下文的 reviewer。它应直接检查需求、代码和运行结果，开发 Agent 的完成总结只能作为查找材料的入口。

Claude Code、Codex 和 GitHub Copilot 的官方资料，都把可运行检查与代码审查纳入开发流程。下面先解释其中的风险，再比较这些主流工具的具体建议。

> 官方资料核验日期为 **2026-11-18**。运费案例、reviewer 提示词和验收流程是本文的工程示例。

<!--more-->

## 1 实现和测试可能共享同一个错误

假设原始需求明确写着：

> 订单金额满 100 元免运费，恰好 100 元也免；不足 100 元收取 8 元运费。

AI 把“满 100 元”理解成“大于 100 元”，写出下面的实现。金额统一以分表示：

```python
def shipping_fee(total_cents: int) -> int:
    return 0 if total_cents > 10_000 else 800
```

随后，它补充了两个测试：

```python
assert shipping_fee(9_900) == 800
assert shipping_fee(10_100) == 0
```

两个测试都通过，函数的两个分支也都执行到了，但恰好 100 元的订单仍然会被收取运费。

| 订单金额 | 原始需求规定的运费 | 当前实现返回的运费 | 原有测试是否覆盖 |
| :--- | :--- | :--- | :--- |
| 99 元 | 8 元 | 8 元 | 是 |
| 100 元 | 0 元 | 8 元 | 否 |
| 101 元 | 0 元 | 0 元 | 是 |

这里没有出现测试框架失效。问题在于测试没有检查需求中明确列出的边界。测试数量和代码覆盖率，都不能单独说明需求覆盖完整。

还有一种更隐蔽的写法：测试根据实现里的同一条条件计算预期值。

```python
expected = 0 if total_cents > 10_000 else 800
assert shipping_fee(total_cents) == expected
```

即使输入包含 100 元，这个测试也会通过，因为错误条件被复制到了两边。

**先写测试也需要独立的判断依据。** 如果测试和实现都建立在同一处误读上，调整编写顺序仍可能保留这个错误。这个例子说明的是一种可能的失败方式，并不意味着 AI 生成的测试普遍无效。

## 2 让预期结果有实现之外的来源

测试需要回答“正确结果应该是什么”。软件测试中通常把这种判断依据称为 **test oracle**。在这个例子里，依据就是需求中的“恰好 100 元也免”，由此可以直接补上：

```python
assert shipping_fee(10_000) == 0
```

这条断言在当前实现上会失败。把 `>` 修正为 `>=` 后，三个金额才都符合需求。

实际项目中的依据可以来自不同地方：

| 判断依据 | 怎样用于验证 | 需要核对什么 |
| :--- | :--- | :--- |
| 原始需求与已确认的验收条件 | 将每项行为对应到输入、操作和预期结果 | 需求版本、边界、例外和单位是否明确 |
| 经业务或领域人员确认的样例 | 固定输入和预期输出，保存为 fixture 或验收用例 | 样例来源以及适用范围 |
| 规范、协议或可信参考实现 | 对照规定行为，或在相同输入下比较输出 | 版本、配置和允许的差异 |
| 已确认正确的历史案例 | 建立回归检查 | 需求变化后，旧预期是否仍然成立 |

AI 可以协助提取验收条件、扩充样例和生成测试代码，但重要样例的正确性需要有可追溯的依据。把当前程序的输出直接保存成 expected，再证明程序与 expected 相同，只能检查输出是否变化。

对于画质算法、检索系统等没有唯一正确答案的任务，可以使用专家确认样本、对照实验、容差和明确的评价维度。预期仍然需要从任务目标出发。输入顺序不影响结果、重复请求保持幂等性等性质检查，也只能在业务确实要求这些性质时使用。

如果需求本身含糊，应先记录歧义并确认。让两个 Agent 对同一句含糊描述达成一致，仍然不能代替需求确认。

## 3 给 reviewer 独立上下文和完整材料

开发会话中已经积累了方案选择、调试过程和大量“为什么这样做”的解释。审查时另开一个上下文，可以减少它继续沿用这些判断的机会。

这里的独立，指 reviewer 不继承开发过程的完整对话，能够从原始需求重新判断。具体工具是否会传入父会话历史，需要核对实际调用方式；给 Agent 换一个角色名称，并不能自动保证上下文独立。

reviewer 至少需要直接访问以下材料：

| 材料 | 它应检查的问题 |
| :--- | :--- |
| 原始需求、后续确认与可信样例 | 实际要交付什么，哪些条件不能遗漏 |
| 当前 diff、相关源码和调用路径 | 改动是否实现了要求，是否影响已有行为 |
| 测试代码、输入数据和预期值来源 | 测试是否遗漏边界，是否重复了实现中的假设 |
| 当前候选版本的运行记录和产物 | 真实执行了什么，观察结果是否支持验收 |

开发 Agent 可以提供文件路径、启动命令和证据位置，帮助 reviewer 找到材料。但如果 reviewer 只读“已完成、已测试、无问题”的总结，它评估的仍然主要是开发者对结果的描述。

审查还应覆盖运行结果：检查命令是否执行成功、测试是否被跳过、mock 是否绕过关键行为，以及截图是否对应需要验收的状态。必要时，在独立测试环境中重跑关键检查。若 reviewer 无法运行，就明确记录这一限制，不能把读过日志写成亲自复现。

下面是工具无关的任务说明，使用时替换路径、版本和运行入口。

```text
你负责审查当前候选改动。请从原始需求重新判断，不预设实现正确。

材料：
- 原始需求与确认记录：<路径或链接及版本>
- 可信样例及其来源：<路径>
- 候选代码、diff 与测试：<工作区和基准版本>
- 运行命令、环境与证据：<路径>

先读取原始材料，独立列出验收条件，再检查代码、测试和运行结果。
开发 Agent 的完成总结仅用于定位材料，不能作为通过依据。

重点检查：
- 需求是否遗漏，边界、单位和异常行为是否符合约定。
- 测试预期是否有依据，是否复制了实现中的错误假设。
- 运行记录是否对应当前代码，关键流程是否真正执行。

不修改候选源码或验收标准。需要复现时使用独立测试环境。
优先报告影响正确性的问题，跳过纯风格偏好。
每条发现给出需求依据、代码位置、触发条件、实际与预期结果。
未发现问题时，说明检查范围、亲自运行的检查和仍未验证的部分。
需求有歧义时列为待澄清，不自行降低验收条件。
```

</details>

不同模型可以提供另一种审查视角，但模型品牌不同，也不能保证错误相互独立。可信依据、上下文安排和实际检查，仍然决定审查能发现什么。

## 4 三种主流工具的官方实践

几家工具的文档入口各不相同，但都要求把生成代码之后的验证做具体。

| 工具 | 官方资料中的具体建议 |
| :--- | :--- |
| Claude Code | 提供能返回通过或失败的检查；要求运行证据；用新的 subagent 审查，并支持逐项对照规格。[Best practices](https://code.claude.com/docs/en/best-practices#give-claude-a-check-to-run) |
| Codex | 按需补充测试、运行相关检查、确认最终行为符合请求，并审查 diff 中的缺陷和回归；`/review` 支持审查未提交改动、提交或相对基准分支的差异。[Best practices](https://learn.chatgpt.com/guides/best-practices#improve-reliability-with-testing-and-review) |
| GitHub Copilot | 认真检查生成代码，并用自动化测试等工具验证；Copilot code review 用于补充人工审查，其反馈也需要核实。[使用建议](https://docs.github.com/en/copilot/get-started/best-practices#check-copilots-work)、[Agent 使用说明](https://docs.github.com/en/copilot/responsible-use/agents) |

其中，Claude Code 当前文档与本文讨论的问题尤其贴近：它说明终端中的 `/code-review` 会在没有见过开发对话的新 subagent 中检查 diff；还给出对照 `SPEC.md` 检查每项要求及边界测试的提示方式，并强调提供实际命令和输出或截图。[独立审查与规格核对](https://code.claude.com/docs/en/best-practices#review-against-your-spec)

从这些官方建议可以归纳出一个共同方向：**把“完成”连接到检查、行为和审查证据。** 本文进一步建议 reviewer 同时检查原始需求、代码和运行结果；这是一套跨工具的工作流设计。

## 5 把独立验证放进一次实际交付

不必为每个小修改配置多层 Agent。先建立一条简短、能执行的流程：

1. **实现前明确验收依据。** 保存当前需求及确认记录，选出关键样例和边界。样例数量由任务决定，重点是能区分正确与错误行为。
2. **开发 Agent 实现并自测。** 它仍然负责运行相关检查、读错误并修复，交付代码和实际结果。
3. **重要改动进入独立审查。** reviewer 从原始材料检查需求覆盖、代码行为、测试预期和运行证据，必要时复现关键场景。
4. **修复后更新验证。** 重新运行受影响检查；候选代码或需求变化后，旧报告需要重新判断是否适用。需求负责人核对业务行为后，再完成约定验收。

证据应当对应要证明的行为：

| 要确认什么 | 合适的证据 | 单独使用时的局限 |
| :--- | :--- | :--- |
| 代码能够构建 | 构建命令、退出状态和输出 | 不能证明业务需求完整 |
| 指定样例符合预期 | 测试输入、断言和执行结果 | 不能证明未覆盖场景正确 |
| 用户能够完成操作 | 实际点击或请求、返回值及必要的状态检查 | 页面能打开不代表流程完成 |
| 界面符合设计 | 对应视口和状态的截图及设计对照 | 截图不能证明按钮行为或数据已经持久化 |

运行记录至少保留候选代码版本、未提交改动状态、环境、命令、结果与产物位置。对于正在修改的工作区，仅记录 Git commit 还不足以定位实际被测代码。

验收状态也应区分清楚：**已验证、验证失败、未验证、需求待澄清**。外部服务不可用时，验证状态就是未验证；mock 测试通过时，已验证范围就是 mock 覆盖的行为。

在运费案例中，一条有效的审查发现可以很短：需求规定 100 元免运费，当前代码使用 `>`；输入 `10_000` 时实际返回 `800`，预期为 `0`。这条发现同时连接了原始需求、具体代码和可复现结果，开发者可以据此修正并重新验收。
