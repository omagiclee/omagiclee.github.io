我负责一个面向多用户的生产级数据平台，工作覆盖需求澄清、前后端、数据库、部署，以及交付后的用户验收。本地的 Data Flywheel 是原型和试验场，公司里的生产平台承接持续进入的真实需求。

目前，我主要使用 GPT-6.1 Sol 等前沿模型，常见工作方式是开启多个窗口，在每个窗口中分别和 AI 对齐需求、讨论方案，再让它执行。这个方式已经能推动开发，但我仍承担大量上下文传递和集成工作：**同一个背景需要重复解释，不同任务之间的接口、进度和修改需要自己协调。**

我的当前判断是：先把需求、项目知识、任务边界和验收证据组织起来，再按任务特点组合交互式、并行和后台 Agent。平台负责人保留优先级、架构取舍和交付判断，AI 逐步承担可独立验证的工程工作。

> **方案状态**：2026-11-02 首版，已形成需求与调研基线，下面的候选工作流仍待真实任务验证。本文使用固定网址持续修订；新需求会更新当前方案，试点结果进入验证记录。工具能力核验截至 **2026-11-02**。

## 1 已确认的需求与当前问题

这里首先记录已经明确的背景，后续选型和流程设计都应回到这些需求。

| 已确认事项 | 对方案的要求 |
| :--- | :--- |
| 负责整个生产级数据平台，承接多个用户的需求 | 同时考虑需求排序、跨模块依赖、运行质量和用户验收 |
| 开发涉及前端、后端、数据库和部署 | 一个功能需要跨层集成，不能只检查局部代码 |
| 已经使用前沿 AI 模型 | 优先研究怎样组织执行、提供上下文和验证结果 |
| 多个窗口分别对齐需求和方案 | 减少重复解释，让决策可以被其他会话准确引用 |
| 多任务协调与集成消耗精力 | 明确任务边界、依赖、接口和最终集成责任 |
| 希望先建立全景认知 | 暂不预先锁定某个工具、自建框架或生产发布的自主程度 |

**生产平台的工作方式是本文的讨论对象。** 本地原型可以验证交互和工程方法，其技术栈、运行记录和测试结果不能直接证明公司平台已经具备相同条件。

评价方案时，我会关注需求到验收的时间、本人投入的协调时间、集成返工和线上回归。Agent 数量、窗口数量和生成代码量，可以帮助分析过程，但不能单独证明交付能力提高。

## 2 先区分模型、Agent、流程与交付系统

讨论 AI 开发时，很多名称实际处在不同层次。

| 层次 | 解决的问题 | 典型组成 |
| :--- | :--- | :--- |
| 模型 | 理解、推理、生成和判断 | GPT-6.1 Sol、Claude 等 |
| Coding Agent | 读取仓库、修改代码、运行工具，并根据结果继续工作 | Codex、Claude Code、Cursor Agent |
| 开发协作流程 | 澄清需求、拆分任务、传递信息、安排并行和审查结果 | 规格驱动开发、主 Agent 与子 Agent、工单驱动 |
| 工程与交付系统 | 提供可运行环境、可信检查、集成发布和运行反馈 | Git、开发环境、CI/CD、监控与需求系统 |

如果一个工具已经能自主查代码、改文件、跑测试和修复错误，它就具备了 Coding Agent 的工作方式。进一步自动化，需要明确它持续追求什么、能调用哪些工具、怎样判断完成，以及失败后如何继续。

例如，Codex Goals 将可验证的目标保存在会话中，支持跨轮次继续推进，并提供暂停、恢复和停止机制。它适合路径需要边做边探索、但终点可以检查的任务。[Codex Goals](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex)

模型选型仍然重要。OpenAI 当前将 GPT-6.1 Sol 定位于复杂、长时间工作，但模型选择本身不会建立共享需求、测试环境和发布流程。[OpenAI 模型说明](https://learn.chatgpt.com/docs/models)

有关执行状态、恢复和验证机制的细节，可继续阅读[Harness Engineering]({{< relref "/posts/vibe-coding/harness-engineering/" >}})。本篇更关注这些能力怎样进入生产平台的整体交付方式。

## 3 主流工作模式怎样组合

这些模式可以叠加。一次复杂需求可能先在交互式会话中澄清，再拆成并行任务，其中部分任务交给后台 Agent。

| 工作模式 | 怎样运行 | 适合的工作 | 协调成本主要在哪里 |
| :--- | :--- | :--- | :--- |
| 交互式单 Agent | 人与一个 Agent 讨论，由它贯穿调查、实现和验证 | 需求不清晰、架构调整、复杂排错 | 需要人的阶段性判断 |
| 多个独立任务并行 | 不同会话分别处理任务，各自使用分支和工作区 | 相对独立的需求或修复 | 依赖、接口和合并顺序 |
| 主 Agent 与子 Agent | 主 Agent 围绕一个目标委派子问题，收集结果并集成 | 跨模块调查、独立实现、审查 | 任务交接、重复阅读和结果检查 |
| 后台 Agent | 明确任务进入独立环境，运行后返回 PR 和验证产物 | 边界清楚的功能、缺陷和维护任务 | 环境准备、上下文供给和自动检查 |
| 事件驱动工程 | 工单、CI 失败或告警触发调查和修改 | 重复维护、回归定位、批量升级 | 调度、去重、恢复和发布边界 |

**并行处理多个需求，与多个 Agent 共同处理一个需求，解决的是不同问题。** 前者提高任务吞吐量，后者利用同一目标中可以独立推进的部分。有顺序依赖的步骤仍需要等待。

从公开调查看，人工参与仍然普遍。Stack Overflow 2026 年年度调查把 human-in-the-loop 描述为主导工作方式；其 4 月约 1,100 人的专项调查中，69% 报告使用单 Agent，63% 很少或从不让 Agent 完全自主运行。专项调查是特定样本，不能直接视作全行业的精确占比。[年度调查](https://survey.stackoverflow.co/2026/ai)、[2026-05-27 专项调查分析](https://stackoverflow.blog/2026/05/27/agents-on-a-leash-agentic-ai-remains-mostly-monitored-at-work/)

### 工具提供了哪些入口

下面比较工作入口和能力侧重，实际选型还要结合公司环境中的代表性任务。

| 工具或方案 | 能力侧重 | 对生产平台的考察重点 |
| :--- | :--- | :--- |
| [Codex](https://learn.chatgpt.com/docs/agent-configuration/subagents) | 交互式开发、子 Agent、持续目标与独立工作区 | 是否能稳定连接项目环境、执行检查并保留交付证据 |
| [Claude Code](https://code.claude.com/docs/en/sub-agents) | 开发会话、子 Agent 与可复用流程 | 项目知识能否准确加载，任务交接是否清楚 |
| [Cursor Cloud Agents](https://prod.cursor.com/help/ai-features/background-agents) | 将远程开发、测试和 PR 产物结合，支持截图、视频和日志 | 公司服务与依赖能否在执行环境中使用 |
| [GitHub Copilot](https://docs.github.com/en/copilot/concepts/copilot-surfaces/copilot-on-github) | 围绕 Issue、PR、审查、CI 和仓库事件组织工作 | 能否融入已有仓库、审查和交付流程 |
| [OpenAI Agents API](https://developers.openai.com/api/docs/guides/agents-api/overview) 等可编程运行框架 | 通过程序调用 Agent，连接自有工具与环境 | 公司特有的调度、状态和工具集成是否值得自行维护 |

多 Agent 的触发和隔离方式需要按产品核对。当前本地 Codex 可通过明确请求，或适用的项目、技能指令触发委派；子 Agent 会增加用量。Claude Code 的 Agent Teams 则仍被官方标为实验功能，默认关闭。[Codex 子 Agent](https://learn.chatgpt.com/docs/agent-configuration/subagents)、[Claude Code Agent Teams](https://code.claude.com/docs/en/agent-teams)

### 规格驱动开发位于流程层

Spec-Driven Development 的实用价值，是把“这次要做什么、什么算完成”保存为可审阅的规格，再连接计划、实现和检查。规格需要随需求与实现变化而维护，文档数量应与任务复杂度匹配。

- [Spec Kit](https://github.github.com/spec-kit/)：组织规格、计划、任务、实现与收敛检查。
- [OpenSpec](https://openspec.dev/docs/quickstart)：围绕变更保存提案、规格、设计和任务，完成后更新项目规格。
- [BMad](https://docs.bmad-method.org/reference/skills-and-agents/)：提供需求、产品、架构、开发和审查等角色与流程。

角色可以由同一会话分阶段承担，也可以由不同 Agent 执行。命名角色之后，任务如何交接、由谁集成、依据什么验收，仍要有具体安排。

## 4 企业案例提供了什么依据

下面是已经公开的工程实践。时间和规模保留为各篇文章发布时的记录；企业自述展示了可行路线，不能直接推出其他团队会得到相同收益。

| 案例 | 公开做法 | 可迁移的经验 |
| :--- | :--- | :--- |
| [Stripe Minions，2026-02-19](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2) | 当时披露每周超过 1,300 个合并 PR 完全由 Minions 产生、经人工审查；任务运行在独立开发环境中，流程交替使用 Agent 与固定程序 | 明确任务、标准环境和确定执行的检查，支撑无人盯守的编码 |
| [Spotify Honk，2026-06-03](https://engineering.atspotify.com/2026/6/code-with-claude-coding-is-no-longer-the-constraint) | 后台 Agent 在 Kubernetes 中并发运行，连接 CI；Fleetshift 负责目标选择、调度和进度管理 | 将平台级任务管理与单次代码修改分开 |
| [Ramp Sheets，2026-03-23](https://labs.ramp.com/research/ramp-sheets-self-maintaining/) | 告警触发沙箱中的复现与修复，合并需工程师审查；增加分诊和状态记录来过滤噪声、避免重复处理 | 运行反馈可以进入开发闭环，事件质量和去重同样重要 |

这些实践都投入了人类开发者也需要的基础设施：项目知识、内部工具、可复现环境、快速反馈和可追踪交付。Stripe 还把运行必要检查等确定步骤直接写进程序，让 Agent 主要处理实现和修复中的动态判断。

DORA 在 2026 年的分析中也指出，编码加速可能将时间转移到审查和验证；AI 会放大已有工程体系的优势与问题。因此，流程收益应沿整个交付链衡量。[DORA 对软件开发生命周期的分析](https://dora.dev/insights/balancing-ai-tensions/)

## 5 候选方案 让需求和工程形成连续交付链

我倾向于先建立统一的需求与交付记录，每条需求有自己的协调会话和执行任务。平台层保留架构规范、需求依赖与发布安排；具体会话只加载当前工作需要的信息。

{{< mermaid >}}
flowchart TD
    U["多用户需求"] --> R["澄清、排序<br/>确定验收标准"]
    R --> P["影响分析与任务拆分<br/>指定集成负责人"]
    P --> E["交互式、并行或后台执行"]
    E --> V["集成、自动验证与审查"]
    V --> D["发布与运行观察"]
    D --> A["用户核对交付并验收"]
    A --> F["验收反馈与线上问题<br/>进入下一轮需求"]
{{< /mermaid >}}

这里有两种完成标准：**工程完成**要求代码、数据库、服务与部署通过约定检查；**需求完成**要求交付解决了用户的问题，并完成约定验收。通过 CI 的 PR 是工程产物，之后仍要关联发布和用户反馈。

### 5.1 用统一记录减少重复对齐

需求系统保存目标、讨论结论、规格修订、优先级和验收结果；代码仓库保存实现及对应版本。两者通过需求标识、任务、PR、提交、发布版本和验证报告关联起来。

每个开发会话开始时，引用统一需求来源及其修订版本。需求变化先更新来源，再通知受影响任务；已有实现和测试也要据此重新判断。不同窗口不会自动拥有相同的对话历史，worktree 中的未提交文档也不会自动同步到其他工作区。

<details>
<summary>展开一份轻量任务说明示例</summary>

下面是协作记录示例，可以放在工单或项目文档中，不是某个 Agent 的配置格式。

```text
目标：本次交付要让用户完成什么操作。
依据：需求链接、当前规格修订与相关架构文档。
边界：本次修改范围，以及需要保持的兼容行为。
依赖：依赖哪些接口、任务或决策；由谁负责集成。
执行环境：启动方法、测试数据、可使用的服务与操作范围。
验证：对应验收场景的检查方法和必要回归。
交付：代码版本、PR、测试证据、运行入口和剩余问题。
```

交接时只补充已完成、已验证、未完成和下一步。测试证据要能定位到代码版本与执行环境，避免用旧报告证明新修改。

</details>

项目上下文也应分层维护：

| 信息或机制 | 应承担的职责 |
| :--- | :--- |
| `AGENTS.md` | 长期工程约定、构建验证入口、模块知识的阅读路径 |
| 项目文档与接口定义 | 架构事实、接口行为、重要决策及版本 |
| 需求规格与任务记录 | 本次目标、依赖、进度、变更与验收 |
| Skills | 可以重复使用的操作流程与脚本 |
| MCP、CLI 或 API | 按需查询需求、文档、构建状态与运行信息，执行授权操作 |
| CI、测试与发布系统 | 执行检查并保存结果，实施交付约束 |

入口规则保持简短，详细知识按模块读取。OpenAI 的定制说明也区分了项目指令、记忆、Skills、MCP 和子 Agent 的不同职责。[Codex 定制机制](https://learn.chatgpt.com/docs/customization/overview)

### 5.2 每条需求明确集成责任

一条需求可以拆给多个执行者，但需要明确谁维护整体方案、处理跨任务变更，并完成最终集成。协调会话可以委派代码定位、日志分析、独立实现和审查；平台负责人仍负责跨需求的架构与优先级取舍。

任务应按独立行为和依赖关系划分。一个后端 API 与它的数据库迁移可能应由同一任务贯穿；前端可以在接口约定稳定后并行。按前端、后端、数据库、部署机械拆成固定窗口，会增加需要跨窗口决定的事项。

并行调查和独立审查通常容易开始；并行写代码还需要约定文件范围、接口所有权和合并顺序。发现公共接口需要变化时，由集成负责人统一更新约定并通知相关任务。

### 5.3 同时隔离代码和运行资源

Git worktree 提供同一仓库的独立检出目录，支持不同分支并行开发；多个 worktree 共享 Git 元数据。[worktree 说明](https://learn.chatgpt.com/docs/environments/git-worktrees)

运行资源需要另外安排：服务端口、数据库或 schema、队列、对象存储前缀和测试账号，都可能成为并行任务之间的共享状态。子 Agent 拥有独立上下文，也不意味着它自动拥有独立目录或数据库。

本地工作区适合快速交互；远程容器或开发机适合承接后台任务。执行地点应由公司服务的可达性、依赖和资源需求决定。标准环境至少要能读取代码、安装或复用依赖、启动相关服务、准备测试数据并运行验证。

### 5.4 把验证和发布接在执行之后

Agent 需要看到测试结果、服务日志和界面行为，才能根据反馈修复问题。确定的检查由脚本和 CI 稳定执行，AI 参与解释失败与修改实现；最终检查应覆盖集成后的版本。

验证按改动分层进行：局部行为检查、接口与数据库集成、关键用户流程，以及必要的性能和兼容回归。独立审查补充另一份判断，测试和运行证据提供可复核依据。

开发与测试中的常规操作可以提前界定授权范围；生产写入、数据库迁移和发布，接入既有发布机制及其检查。Agent 任务也需要有预算、失败恢复和结束条件，明确什么时候继续修复，什么时候等待必要信息或交还处理。

## 6 用数据集异步导出走一遍

以下使用“新增数据集异步导出”解释协作方法，这是设计示例，不表示该需求已经提出或实现。

### 先明确行为 再安排并行

需要与用户确认数据规模、输出格式、项目权限、取消与重试行为，以及什么情况下算导出成功。任务状态、接口和数据一致性的约定形成之后，再决定哪些部分能够独立开发。

{{< mermaid >}}
flowchart TD
    S["确认需求与验收场景"] --> C["确定接口、任务状态<br/>与数据一致性约定"]
    C --> A["API 与数据库迁移"]
    C --> F["前端交互<br/>按约定接口开发"]
    C --> W["导出执行与故障恢复<br/>实现可独立部分"]
    A --> J["集成相关任务"]
    F --> J
    W --> J
    J --> T["真实链路与必要回归"]
    T --> R["发布、观察与用户验收"]
{{< /mermaid >}}

图中的并行以依赖允许为前提。例如，执行器依赖尚未实现的公共逻辑时，可以先验证独立部分，再等待集成。接口变化需要同步到前端和执行器任务。

### 验收覆盖数据与执行行为

| 场景 | 应观察的结果 |
| :--- | :--- |
| 正常提交与下载 | 任务状态、导出文件和页面结果一致，数据内容符合规格 |
| 跨项目访问 | 用户只能操作与读取授权范围内的任务和产物 |
| 重复请求、失败重试 | 按约定的幂等与重试语义执行，不产生意外重复副作用 |
| 取消、进程重启、依赖失败 | 状态可解释，恢复或终止行为符合约定 |
| 旧库升级 | 旧记录保留，应用与迁移版本兼容 |
| 代表性数据规模 | 时间、资源和产物大小满足评审中确定的指标 |

自动化检查完成后，将 PR、代码版本、迁移说明、测试报告和交付入口关联到需求。发布后观察成功率、耗时和异常，再由用户核对约定场景。性能阈值与生产发布方式需要按实际环境确定。

## 7 建议怎样开始试行

当前最值得先验证的假设是：**统一上下文与集成责任，能够减少我的重复对齐和协调投入。** 试点先沿用现有开发工具，选择一条有明确验收场景、涉及多个层次的常见需求。

| 阶段 | 要验证的改进 | 进入下一阶段的依据 |
| :--- | :--- | :--- |
| 统一需求与交付记录 | 一份需求来源、明确集成责任、关联验证和发布 | 新会话可以恢复目标，集成返工原因可追踪 |
| 规范并行与复用流程 | 独立任务使用工作区，重复操作整理为 Skills 或脚本 | 并行确实节省时间，环境与接口冲突可控制 |
| 引入后台任务 | 明确工单在标准环境中执行，返回 PR 和证据 | 人可以离开执行过程，结果仍可检查和接手 |
| 扩展事件驱动 | 从具体 CI 失败、告警或维护任务触发处理 | 分诊、去重、恢复和交付流程已有稳定记录 |

这些是候选演进步骤，当前尚未决定引入自建调度平台。若现有工具能够满足任务管理与执行需求，就先用实际反馈判断还缺什么。

### 用整条交付链评价效果

| 指标 | 记录方式 |
| :--- | :--- |
| 需求到验收的时间 | 分别记录澄清、开发、等待、集成、发布和验收耗时 |
| 本人协调投入 | 记录补背景、解释已有决策、处理冲突和催促验证的时间 |
| 集成返工 | 按接口变化、需求理解、环境冲突和实现缺陷分类 |
| 工程质量 | 记录缺陷、回滚、关键回归与交付后修复 |
| 执行成本 | 同时记录模型用量、计算资源、审查与返工投入 |

比较复杂度接近的任务，并保留样本数与适用范围。后台任务能产生更多 PR 时，也要观察审查、发布和验收是否成为新的等待点。

## 8 根据新需求持续完善方案

本文保留一份当前有效的方案，修改历史由 Git 保存，重要变化在本节登记。后续补充需求时，按下面的顺序维护：

1. 更新已确认需求，保留观察日期；当前明确更正覆盖旧假设。
2. 判断变化影响需求组织、任务拆分、上下文、执行环境还是验收，修订对应方案。
3. 将待试行的设计与实际运行结果分开；验证记录关联具体任务、版本和证据。
4. 根据结果保留、调整或移除流程组件，同时更新正文与变更记录。

| 常见需求类型、依赖和并发情况 | 拆分粒度、并行上限与调度需求 |
| 仓库布局及跨服务依赖 | 工作区组织、接口协调和集成顺序 |
