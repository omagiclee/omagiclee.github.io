AI 已经能写出一批代码，工程师却仍要打开页面、截图、复制日志、检查结果，再把问题描述给 AI。代码生成加快了，验收时的人力投入却可能继续增加。

OpenAI 在 **2026 年 2 月 11 日**发布的 [Harness engineering](https://openai.com/index/harness-engineering/) 案例，讨论的正是这一变化：人的投入转向目标、环境与反馈，让 Agent 自己取得运行证据，完成更多验证工作。

放到影像画质及相关数据平台工作中，我最想先尝试的是：**让 Agent 自主验证评测平台的一条用户路径，再承担版本回归的执行、取证和异常整理，让人集中处理需求取舍与画质判断。** 先把具体任务做扎实，再考虑扩大自动化范围。

> **阅读范围**：官方资料核对截至 **2026-11-18**。第一节概述 OpenAI 的公开案例；后面的画质任务、目录、接口与试点均为本文提出的设计，尚无业务实测收益。本文接续 [Harness Engineering 总览]({{< relref "/posts/vibe-coding/harness-engineering/" >}})，重点讨论如何应用。

## 1 OpenAI 把什么交给了 Agent

Ryan Lopopolo 描述的是一个从空仓库起步的产品实验：约五个月内合并约 1,500 个 PR，最初由三名工程师推动，后来团队增至七人。其做法可以归纳为四项。

{{< codex-table label="OpenAI Harness engineering 案例的关键做法" >}}
| 环节 | 公开案例中的做法 |
| --- | --- |
| 传递知识 | 简短的 `AGENTS.md` 提供入口，详细知识放在版本化的仓库文档中 |
| 运行环境 | 每个 Git worktree 可启动独立应用实例 |
| 取得证据 | 通过 Chrome DevTools Protocol 操作页面，读取 DOM 与截图；查询隔离环境的日志、指标和链路 |
| 形成反馈 | 让 Agent 检查和迭代修改，用自定义 lint 与结构测试约束架构 |
{{< /codex-table >}}

来源：[OpenAI 工程原文](https://openai.com/index/harness-engineering/)。这是特定团队的新产品经验，PR 数量不能证明交付质量，也不能预测画质团队能节省多少 QA 时间。

由此出发，我会先检查团队里哪些验收劳动反复出现：人是不是总在帮 AI 找同一种日志，核对同一类配对错误，解释同一个指标口径？这些重复动作值得逐项做成可调用、可检查的能力。

## 2 把人的三项工作变成具体交付物

“明确意图、准备环境、建立反馈”很容易停留在口号。对一次实际任务，可以分别要求三份可审阅的交付物。

{{< codex-table label="人需要准备的三项交付物" >}}
| 人负责什么 | 应留下什么 | 影像画质工作中的例子 |
| --- | --- | --- |
| 明确意图 | 目标、范围、不可破坏项与完成条件 | 比较降噪 A/B；分别检查噪声、纹理、肤色；不改评测口径 |
| 准备环境 | 能运行的版本、固定输入、工具入口与产物位置 | 固定模型和 ISP 配置；读取同一批输入；保存全图与原尺寸局部 |
| 建立反馈 | 检查规则、失败原因、人工分歧及其处理方式 | 配对缺失直接失败；视觉证据不足进入复核；确认的缺陷加入回归集 |
{{< /codex-table >}}

最需要人先做判断的，是取舍。例如，“夜景更干净”可能伴随纹理损失，肤色偏暖也可能来自场景光源。没有明确的比较条件和优先级，Agent 即使完整执行流程，也可能优化错目标。

OpenAI 的 [AI 原生工程团队指南](https://learn.chatgpt.com/docs/guides/build-ai-native-engineering-team)同样强调，工程师仍要确保测试覆盖需求，并检查模型生成的测试是否走了捷径；Agent 能跑测试，并不意味着测试已经表达了正确目标。

### 先区分软件验收与画质判断

在画质平台上，两类问题经常出现在同一个页面里，但证据要求不同。

{{< codex-table label="软件验收与画质判断的证据区别" >}}
| 要验证的问题 | 合适的检查方式 | 通过以后能说明什么 |
| --- | --- | --- |
| 切换样本后，A/B 是否仍正确配对 | 检查样本 ID、资源请求、版本字段与实际图像 | 查看器展示了约定的输入和输出 |
| 评测任务是否跑完 | 核对预期数量、成功与失败清单、产物完整性 | 这批任务的执行状态清楚 |
| 指标是否计算正确 | 用已知输入检查计算、ROI、颜色域与归一化 | 指标符合定义 |
| 皮肤是否自然、细节是否保留 | 统一显示条件，结合独立人工盲评 | 在指定样本和观看条件下获得偏好证据 |
{{< /codex-table >}}

页面截图能帮助定位“图片显示错了”，但不能单独证明“新版本画质更好”。尤其是 HDR、广色域和高分辨率内容，还要说明 Agent 实际看到了什么：缩略图、经过映射的预览，还是带颜色信息的原始产物。

## 3 开发平台时，让 Agent 自己复现和验证缺陷

先看一个软件工程场景：**在 A/B 评测查看器中快速切换样本，左侧已显示新样本，右侧仍残留上一张结果。** 这是本文构造的缺陷示例，适合用来说明怎样减少人工 QA 的反复转述。

如果人只说“切图偶尔不对，修一下”，Agent 很可能改完代码后让人再点一次页面。更完整的任务应明确：切换样本、切换版本和调整 ROI 后，两侧图像及导出记录都必须对应当前选择；慢请求晚返回，也不能覆盖当前结果。

我会让 Agent 按下面的流程交付：

1. **在隔离环境复现。** 用固定的两个样本和两个版本启动应用，在测试环境延迟旧请求；通过浏览器切换并记录请求顺序、当前样本和实际图像身份。
2. **用运行证据定位。** 把浏览器网络请求与后端日志关联，区分响应乱序、缓存键错误、后端配对错误等可能原因。截图记录现象，图像摘要和版本字段用于核对身份。
3. **先留下失败检查，再修复。** 将确认的触发路径变成能稳定失败的检查，随后修改实现，并验证修复前后行为不同。
4. **沿完整用户路径回归。** 重新检查快速切图、切换版本、加载失败和导出报告；核对导出的样本、ROI 与版本和页面一致。

最后提交代码差异、复现步骤、检查结果，以及关联到同一次运行的截图和日志。如果任务还包含速度要求，应先约定测量条件与阈值，再记录修改前后的耗时。

这里人工验收的对象变得具体：需求是否完整、证据能否支持修复、相关路径是否遗漏。人工无需先替 Agent 重走一遍页面，才能告诉它下一条错误。

这类平台缺陷很适合作为起点：它有明确的身份与状态约束，验收结果通常比“图片是否更自然”更容易固定。下面再看如何把取证能力用于画质评测本身。

## 4 使用平台时，让 Agent 完成一次降噪回归

假设团队要比较同一批输入经过基线 A 和候选 B 后的结果。人提出的问题是：**B 是否减少了噪声，同时保留人物纹理和自然肤色？**

第一轮可以让 Agent 负责运行与整理，由工程师判断候选能否进入下一轮验证。整个流程如下。

{{< mermaid >}}
flowchart TD
    H["人定义目标<br/>样本范围与验收条件"]:::client
    P["Agent 核对版本与输入<br/>检查配对和工具可用性"]:::service
    R["执行固定评测流程<br/>保存日志 指标与图像"]:::engine
    C["检查完整性与回归规则<br/>按场景整理异常"]:::engine
    E["生成可追溯报告<br/>全图 局部 运行记录"]:::storage
    J["人审阅疑难与抽样正常样本<br/>完成画质取舍"]:::client
    K["确认的新问题<br/>进入规则或回归样本集"]:::storage
    H --> P --> R --> C --> E --> J
    J --> K
    K --> P
{{< /mermaid >}}

图中评测执行器可以是已有脚本或服务。Agent 主要处理取证顺序、异常调查与报告组织；样本配对、数量核对和固定计算继续交给确定性的程序。

### 任务开始前，冻结比较条件

至少固定输入清单、A/B 版本、推理与 ISP 配置、评价协议，以及用于比较的 ROI。对于视频，还应固定片段、帧范围和时间对应关系。

每次运行保存一份 manifest，记录这些版本和输入摘要，并为产物分配 `run_id`。如果同一输入需要多次随机推理，应保存各次 seed，并报告波动；无法完全复现的部分也要写明。

同内容、同坐标的 A/B 配对，是这里的基本条件。如果有参考图，才进一步按评价协议使用全参考指标；没有可靠参考时，不应为了得到一个分数而构造“真值”。

### 给 Agent 一份能执行的任务约定

下面的文本可作为首次试点的任务模板。样本规模和预算只是示意，实际值应按团队资源填写。

```text
目标：比较基线 A 与候选 B 的夜景人像降噪表现。
输入：已冻结的样本清单、版本与配置，评价协议 v1。
范围：使用现有评测流程；最多完整运行一次，失败分片最多重试一次。

开始前：
- 核对每个样本的 A/B 配对、尺寸、颜色信息与 ROI。
- 确认工具能读取实际图像；仅有文件路径时不能作视觉判断。
- 如发现输入或协议缺失，记录问题，暂停受影响项。

必须交付：
- 预期、成功、失败和跳过数量，及逐项原因。
- 按场景分组的结果、回归候选与证据位置。
- 可打开的全图、原尺寸局部、日志和运行 manifest。
- 未执行检查及其影响；需要人工回答的具体问题。

完成条件：
清单中的每项均有状态，产物可追溯，报告可重放。
画质是否接受另行记录，由人工评审作出判断。
```

这份约定把“评测执行完成”和“候选画质被接受”分别记录。即便所有程序正常退出，候选版本也可能存在明显画质回归。

## 5 准备环境：让 Agent 找得到、跑得动、看得清

环境准备可以从已有仓库增加几个稳定入口开始。建议先用一个 Agent 跑完整个任务，观察它在哪一步需要人工搬运信息。

### 知识入口围绕真实问题组织

入口文档回答如何启动、在哪查协议、到哪找产物，以及哪些问题必须交给人判断。详细材料按主题维护，例如：

```text
AGENTS.md                    # 任务入口、运行命令与关键约束
docs/quality/
  evaluation-protocol.md      # 评价维度、显示条件与统计口径
  data-contract.md            # 样本、版本、配对与 ROI 定义
  known-failures.md           # 已确认缺陷及反例
  review-guide.md             # 人工评审示例与争议处理
tools/quality/               # 现有评测与取证工具
```

例如，`known-failures.md` 可以同时保留“磨皮导致纹理丢失”和“自然景深不应判为失焦”的例子。每个条目包含适用条件、证据与确认日期，避免只留一句笼统规则。

### 一个运行 ID 贯穿页面、日志和指标

我会优先打通下面这些查询。这里是本文设计的能力名称，**不对应 OpenAI 产品的现成 API**。

{{< codex-table label="画质评测任务所需的最小工具能力" >}}
| 能力 | 应返回的证据 |
| --- | --- |
| 查询样本与版本 | 输入摘要、A/B 版本、配对关系、颜色与尺寸信息 |
| 运行评测 | `run_id`、执行状态、失败项和产物索引 |
| 查看图像或片段 | 全图、原尺寸裁剪；视频另含帧号、时间戳和相邻帧 |
| 查询日志与指标 | 按 `run_id` 过滤的错误、耗时、资源使用和任务统计 |
| 打开评测页面 | 对应版本与样本的固定链接，供浏览器验证和人工复核 |
{{< /codex-table >}}

统一身份以后，Agent 才能把“查看器里这张异常图片”与“哪次执行、哪个配置、哪条错误”关联起来。运行耗时、显存等工程指标应与噪声、纹理等画质指标分别呈现，避免把执行成功解释成质量达标。

如果已有日志和指标系统，就增加适用的查询入口；小规模试点也可以先用结构化日志、结果文件和本地报告。选型取决于实际规模，第一轮主要验证证据能否连起来。

### 隔离要覆盖数据与计算资源

代码可以使用独立工作区，任务还需要自己的配置快照、输出目录、缓存命名空间和运行标识。GPU 并发和配额也应由执行器管理，否则几个独立目录仍可能争用同一设备。

首次试点可只读取冻结样本，向任务目录写入候选报告。基线、评价协议与发布状态由既有流程维护。这样能清楚比较每次尝试，也方便复盘错误。

## 6 建立反馈：让报告指出下一步该看什么

报告的价值在于缩短人找到有效证据的时间。只有一张平均分表，工程师通常仍要重新翻遍图像。

### 自动检查分成三个层次

{{< mermaid >}}
flowchart TD
    A["第一层 数据与执行<br/>版本 配对 数量 产物完整性"]:::engine
    B["第二层 按协议计算<br/>分场景指标与回归候选"]:::service
    C["第三层 人工复核<br/>视觉取舍 分歧与正常项抽样"]:::client
    F["执行或数据问题<br/>修复后重跑受影响项"]:::storage
    D["记录评审决定<br/>保留条件与证据"]:::storage
    A -->|有效| B
    A -->|无效| F
    F --> A
    B --> C --> D
{{< /mermaid >}}

第一层没通过时，相应样本不能被统计成“画质通过”。第二层负责按既定协议找信号，第三层检查这些信号是否符合实际观感，并发现自动检查漏掉的问题。

OpenAI 的 [Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)建议用真实任务分布设计评估，并用人工反馈校准自动评分；它也提醒模型裁判可能受答案顺序等因素影响。迁移到画质评价时，以下做法属于本文的应用建议。

- 分别呈现噪声、细节、肤色等维度，保留它们之间的取舍。
- 按低光、逆光、运动、肤色和纹理等场景查看分布，定位平均数掩盖的回归。
- 在统一显示条件下随机排列 A/B，隐藏版本身份，记录无法区分和评审分歧。
- 抽查自动判断正常的样本，同时审阅告警样本，才能估计漏报。

模型可以提出可疑区域、描述现象和组织对比。它的判断仍需要在独立标注上检验；换一个模型投票，也不能直接建立参考真值。关于视觉取证方法，可继续看 [Agentic IQA]({{< relref "/posts/agent-ai/agentic-iqa/" >}})。

### 每条异常要有一份能复核的证据

建议固定报告字段：

{{< codex-table label="单条画质异常的证据字段" >}}
| 字段 | 内容要求 |
| --- | --- |
| 身份 | `run_id`、样本 ID、A/B 版本与配置 |
| 观察 | 在哪个部位、什么尺度看到了什么现象 |
| 证据 | 全图、固定坐标局部；必要时附视频时间范围 |
| 计算 | 指标定义、ROI、计算条件与原始结果 |
| 解释 | 疑似原因、支持依据，以及仍需排除的因素 |
| 下一步 | 建议检查什么，由谁回答哪个问题 |
{{< /codex-table >}}

例如，一条**示意报告**可以写成：“B 的面颊局部更平滑，邻近衣料细纹也有减弱；请在原尺寸下比较这两个固定 ROI。当前证据不足以区分降噪增强与输入缩放错误，需要核对解码尺寸和推理配置。”

这里观察与原因假设分别记录。工程师可以直接验证下一步，而无需先判断一段肯定语气的结论是否可信。

### 反馈还要检查评价器本身

如果发现一条检查让明显错误的产物通过，应先修评价器，再继续比较候选。OpenAI 对 [编码评测的审计](https://openai.com/index/separating-signal-from-noise-coding-evaluations/)发现，测试既可能漏查需求，也可能要求题目没有说明的实现细节。这提醒我们，自动验收规则本身也要有反例验证。

在画质平台中，可以用已确认的 A/B 交换、缺失输出、错误 ROI 等故障检查流程能否报警；涉及视觉判断时，再用独立人工标注的缺陷和正常样本检验。确认有效的检查进入回归，存疑规则继续保留为待核项。

## 7 用两周验证这套做法是否值得继续

建议先选**一个算法任务、一个固定样本集、一套已有评测流程**。影像数据与评测平台的接口约束通常更容易先固定，因此优先试点“回归执行与异常报告”；后续再探索受约束的参数建议或 Auto-GT 候选筛选。

两周是试点安排，能否完成取决于现有工具和环境准备程度。

{{< codex-table label="两周试点的建议安排" >}}
| 阶段 | 工作 | 需要留下的结果 |
| --- | --- | --- |
| 第 1—2 天 | 人工完整做一次，记录查找、运行、复核和返工时间 | 当前流程基线，以及人工判断发生在哪里 |
| 第 3—5 天 | 接通样本、执行、图像、日志与报告入口 | Agent 能重放同一任务，失败有明确原因 |
| 第 6—8 天 | 用已知故障和已标注样本检验检查规则 | 检查能发现什么，会漏掉什么，哪些误报需要修正 |
| 第 9—10 天 | 在预留任务上运行，进行盲评与正常项抽样 | 人工时间、漏报、误报、返工与计算成本的对比 |
{{< /codex-table >}}

预留任务应与开发、调参用的样本分开。样本量与可接受错误率由团队根据风险确定；少量样本全部通过，只能说明这次没有观察到错误。

判断是否继续，我会看四个量：

- **人的总投入**：包括准备环境、维护规则、复核和返工。一次性建设成本单列，再估计多少次运行能够摊平。
- **漏报与误报**：在已知标签或独立抽样复核中，分别统计缺陷漏掉多少、正常项被误报多少；分母与检查范围一起报告。
- **证据可复核性**：另一位工程师能否从报告定位同一运行、样本和结果。
- **任务成本与等待时间**：包括推理、GPU、重试及排队，避免把人工节省变成无边界的计算支出。

试点前应约定继续标准。例如，人工投入需要减少到什么程度，已知关键缺陷是否必须全部检出，以及抽样漏报允许处于什么范围。这些目标应由现有质量要求确定，不能从 OpenAI 的团队经验直接换算。

## 8 我会先从哪一步做起

对于正在用 AI 开发画质数据或评测平台的工程师，我建议拿最近一次真实回归任务做起点：把执行入口、样本身份、图像证据、日志和完成条件连起来，交给一个 Agent 跑完整次流程。每次仍需人工接手的地方，都记录具体原因。

若原因是找不到版本、打不开产物或不知道指标定义，就补环境和文档；若原因是纹理与噪声的取舍没有共识，就先完善评价协议和评审示例。两类问题需要不同投入。

我最希望看到的首轮交付，是一份工程师打开就能开始复核的报告：**这次跑了什么、哪里可能变差、证据在哪里、还有哪些判断需要人作出。** 有了这份报告，下一轮才有依据讨论该把哪些工作继续交给 Agent。
